# ADR-0077: Новая база MRS2 считается с `order_limit_fill_plus_tick = true`

**Status:** Accepted (решение пользователя 2026-10-17)
**Date:** 2026-10-17
**Contract:** [генератор периодных CSV MRS2](../specs/2026-10-16-mrs2-period-csv-generator.md)

## Context

Тестер Hamster исполняет лимитную заявку при касании уровня
(`order_limit_fill_plus_tick = false`) или только когда цена прошла за уровень
хотя бы на тик (`true`). Второй режим консервативнее и ближе к реальной бирже:
касание не означает исполнения, перед заявкой стоит очередь.

Эталон `grid750` и все прошлые прогоны тестера посчитаны при `false`. Базу
анализа CSV Direct строим заново: исторические периоды считает симулятор MRS2,
последний период каждой пары — настоящий тестер. Это удобный момент, чтобы
выбрать один режим для всех новых данных.

Режим меняет результаты: на KORU 2026-08-28…09-17 при `true` ни один из 16
контрольных списков сделок не совпал с режимом `false`, сделок меньше (1826
против 1984). Симулятор воспроизводит оба режима одинаково хорошо.

## Decision

1. Все новые периоды базы MRS2 считаются с `order_limit_fill_plus_tick = true`:
   и симулятором, и настоящим тестером для последнего периода.
2. Режим хранится в настройках прогона генератора (`RunSettings.limit_fill_plus_tick`)
   и пишется в журнал каждого периода (`limit_fill_plus_tick`). Генератор
   получает версию `mrs2-sim-2`.
3. Периоды, посчитанные в разных режимах, не смешиваются в одной оценке READY.

## Consequences

- Эталон `grid750` (режим `false`) больше не служит сверкой для новой базы.
  Сверка симулятора ведётся по полным прогонам тестера в режиме `true`.
- Пороги READY v4, подобранные на данных `false`, нужно пересчитать на новой базе.
- Прошлые CSV и PerformanceDB-данные в режиме `false` остаются как есть и не
  сравниваются с новыми напрямую.
