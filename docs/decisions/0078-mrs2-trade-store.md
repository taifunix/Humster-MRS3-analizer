# ADR-0078: Единое хранилище MRS2 — сделки и часовые ряды вместо сводных баз и CSV Direct

**Status:** Accepted (решение пользователя 2026-10-17; реализация по этапам)
**Date:** 2026-10-17
**Contracts:** [история и выборочные прогоны тестера (черновик)](../specs/2026-10-17-mrs2-history-store-and-tester-sampling.md), [симулятор и генератор периодов](../specs/2026-10-16-mrs2-period-csv-generator.md), [ADR-0077](0077-mrs2-base-limit-fill-plus-tick.md)

## Context

Анализ MRS2 прошёл три схемы хранения:
1. Source v6 → материализация → база анализа: три базы, Source v6 до 40 ГБ на
   файл, эквити разреженная, сделки потеряны из-за проверки объёма в исходных
   прогонах.
2. CSV Direct: одна база анализа из `reports_history.csv`. Тестер в CSV-режиме
   не отдаёт сделок и эквити, поэтому история хранилась фиксированными
   20-дневными периодами без возможности перенарезки.
3. Теперь есть симулятор MRS2 на минутных свечах тестера (секунды на пару и
   период, ранговая корреляция с тестером 0,97–1,00) и выборочные прогоны тестера
   с таблицей сделок.

Проверено 2026-10-17:
- нарезка одной непрерывной симуляции на 20-дневные окна совпадает со свежими
  прогонами окон (KORU, SNOW, XOM: 93–96 % точек во всех допусках, ранговая
  корреляция 1,000, включая Ulcer);
- отбор 10 % лучших точек по симулятору с соседями по кубу (около 28 % сетки)
  содержит 99 % из 10 % лучших точек по полному прогону тестера (5 пар,
  `order_limit_fill_plus_tick = true`).

## Decision

1. **Факты, а не сводки.** Хранятся неизменяемые факты: минутные свечи (папка
   данных тестера, докачка по запросу) и сделки каждой точки сетки. Всё
   остальное (метрики окон, оценки зон, READY) — производное и пересчитывается
   детерминированно.
2. **Формат — Parquet, каталог — DuckDB.**
   - Сделки: неизменяемые сегменты `trades/<биржа>/<пара>/<источник>_<начало>_<конец>_<версия>.parquet`,
     источник `simulator` или `tester`. Более новый сегмент закрывает старый
     через каталог; файлы не переписываются и не удаляются.
   - Часовые ряды маржин-баланса каждой точки (закрытие, минимум, максимум
     часа) хранятся как кэш, пересобираемый из свечей и сделок.
   - Каталог DuckDB: реестр точек сетки, сегменты и их хеши, версии движка и
     правил, режим `plus_tick`, очередь заданий тестера, результаты READY.
3. **Окна по запросу.** Метрики любого окна (в том числе обучение на
   нескольких 20-дневных периодах) считаются нарезкой истории; когда нужна
   строгая семантика тестера, окно пересимулируется свежим прогоном.
4. **Тестер — по выборке.** Для последнего окна (~20 дней) детерминированное
   версионированное правило отбирает точки по результатам симулятора (база:
   10–20 % лучших плюс соседи по кубу). Выборка режется на прямоугольные блоки
   конфигов тестера; очередь заданий в каталоге выполняется исполнителем
   (сначала локальный тестер на сервере, удалённый исполнитель через
   синхронизацию папок — по необходимости). HTML разбирается в сегменты
   сделок `tester` и удаляется.
5. **Место.** Хранилище, симулятор и анализ — на сервере (Windows Server 2022,
   36 ядер). Исполнитель тестера сменный.
6. **Заморозка.** CSV Direct (`feat/csv-direct-analysis`) не развивается;
   экспорт в формат `reports_history` остаётся опцией. Source v6,
   материализация и прежние базы анализа — исторические источники, в новую
   схему не переносятся.

## Consequences

- История любой пары доступна со сделками и точной (поминутно
  восстанавливаемой) эквити; окна любой длины без повторных прогонов.
- Объёмы: сделки ~1–2 ГБ на всю базу, часовые ряды ~5–10 ГБ; задания тестера —
  килобайты, результаты ~100–150 МБ на период.
- Нагрузка тестера снижается в 3–4 раза (около 28 % сетки на пару и период).
- Каждый новый период заново измеряет согласие симулятора и тестера на
  отобранных точках.
- Нужны новые компоненты: хранилище сегментов, кэш часовых рядов, анализ окон,
  READY из хранилища, отбор и очередь тестера, разбор HTML, Panel. Реализация
  идёт этапами, каждый со своей спецификацией и проверкой.
