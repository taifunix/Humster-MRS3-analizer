# ADR-0081: Синхронизация реестра пар через git — файлы по машинам, идентичность строк

**Status:** Accepted (реализация — этап 5 реестра пар, 2026-10-19).
**Date:** 2026-10-19
**Contracts:** [реестр пар](../specs/2026-10-18-pair-registry.md) («Storage and sync», «Stage 5 contract»).

## Context

Спецификация реестра (решение пользователя 2026-10-18) синхронизирует между
машинами только «наши» таблицы: `decisions`, `pair_settings`, `pair_tests`,
`finalists` и снимок `pipeline`. Они лежат текстовыми файлами в отдельном
приватном git-репозитории. Запись выгружается сама, а «Синхронизировать»
сначала подтягивает изменения.

При реализации всплыли три проблемы.

1. **Одна общая строка на таблицу даёт конфликты слияния.** Строки
   дописываются в конец файла. Если обе машины допишут строку, git увидит
   две вставки в одном месте и не сольёт их сам.
2. **`seq` — локальный счётчик.** Строка с другой машины получает новый
   локальный `seq`. Правило «действует строка с наибольшим `seq`» тогда
   выбирало бы не самую позднюю запись, а самую позднюю импортированную.
3. **Ключ `pair_tests.source` вида `perfdb:<result_id>`** уникален только
   внутри одной PerformanceDB. На двух машинах одинаковые номера результатов
   означают разные тесты.

## Decision

1. **Файл на таблицу и машину:** `<table>/<machine>.jsonl`. Каждая машина
   пишет только свои файлы, поэтому слияние git всегда проходит без
   конфликтов. Строка файла — JSON-массив значений в фиксированном порядке
   столбцов. Первая строка — заголовок со списком столбцов. Кодировка UTF-8,
   перевод строки LF, строки отсортированы по ключу.
2. **Идентичность строки.** В `decisions`, `pair_settings` и `finalists`
   появляются столбцы `origin` (машина, где строка создана) и `row_id`.
   - Локальные строки получают `origin` этой машины при первой выгрузке.
     `row_id` — sha256 от `origin`, локального `seq` и содержимого.
   - Импорт добавляет строку, если её `row_id` ещё нет. Импортированные
     строки сохраняют своё происхождение и никогда не выгружаются повторно.
   - В `pair_tests` `origin` тоже появляется. Строка другой машины хранится
     под ключом `<origin>:<source>`, поэтому номера результатов двух
     PerformanceDB не сталкиваются.
3. **Действующая запись определяется по времени.** Действует строка с самым
   поздним `created_ms`, а при равенстве — с большим `seq`. Для одной машины
   это прежний порядок, так как время создания растёт вместе с `seq`.
4. **`pipeline`.** Каждая машина выгружает свою последнюю строку по (биржа,
   пара, сторона). При импорте строка с тем же ключом и днём заменяет
   локальную, только если её `computed_ms` новее.
5. **Push только в настроенный удалённый репозиторий.**
   - Локальный репозиторий синхронизации (`pair_registry.sync.path`, по
     умолчанию `<root>/sync`) создаётся командой
     `python -m mrs3.pair_registry sync-init [--remote URL]`.
   - Выгрузка и коммит делаются всегда, когда этот репозиторий есть.
   - Pull и push — только если у него задан remote `origin`.
   - Приватный репозиторий на GitHub создаёт пользователь:
     `gh repo create <имя> --private`. Сам код ничего на GitHub не создаёт.
   - Если push отклонён из-за чужих коммитов, делается один pull и одна
     повторная попытка push.
6. **Одна синхронизация за раз и атомарные файлы.**
   - Pull с импортом и выгрузка с коммитом и push выполняются под блокировкой
     ОС на файле `.git/mrs3-sync.lock`. Она общая для Panel и CLI.
   - Файл пишется во временный файл в `.git`, затем переименовывается, так что
     прерванный процесс не оставляет полфайла.
   - Строки append-only таблиц, уже записанные в собственный файл, при записи
     сохраняются (объединение по `row_id`). Поэтому снимок, сделанный раньше
     выгрузки другого процесса, не теряет строк.
   - Битый файл останавливает импорт с понятной ошибкой: реестр не меняется.
   - Неудачное слияние git прерывается через `merge --abort`.

## Consequences

- Схема реестра меняется: добавляются столбцы `origin` и `row_id`. Старые
  строки получают их при первой выгрузке, данные при этом не теряются.
- Если две машины задать с одинаковым именем, они будут писать в одни и те
  же файлы, и слияние остановится с ошибкой. Поэтому имя машины берётся из
  `pair_registry.machine` (только `A-Z a-z 0-9 . _ -`), а если оно не задано —
  из имени компьютера. Недопустимые символы в имени компьютера заменяются на
  `_`, и к имени добавляется короткий хеш исходного имени. Так кириллическое
  имя компьютера не ломает реестр, а два таких имени не совпадают.
- Данные реестра никогда не попадают в репозиторий проекта (CLAUDE.md).
