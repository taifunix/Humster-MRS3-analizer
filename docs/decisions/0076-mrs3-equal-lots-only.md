# ADR-0076: Стратегии MRS3 генерируются только с лотами EQUAL

**Status:** Accepted (решение пользователя; реализация не начата)
**Date:** 2026-10-16
**Evidence:** [план проверки плато v4, раздел «Лоты EQUAL против INCOME»](../superpowers/plans/2026-10-15-plateau-v4-validation-plan.md)

## Context

Для каждой READY-структуры из 2–3 ордеров генерируются два JSON-варианта:
- `EQUAL` — равные лоты;
- `INCOME` — лоты пропорциональны доходности MRS2-точки ордера на обучении.

Оба варианта проходят тик-тест MRS3.

INCOME почти всегда отдаёт мелкому ордеру большую часть лота: медиана доли первого ордера — 0,63. Глубокие усредняющие ордера получают малую долю.

Проверка проводилась на PerformanceDB `performance-v2-bybit_ohlc4_old`. Там 5135 пар одинаковых структур, фиксированный лот 10 000 USDT. Тесты почти целиком лежат внутри окна анализа, по которому подобраны веса INCOME.

- **На всём окне теста** INCOME выше по доходности (+3,7 п.п./мес), но и просадка выше (+0,57 п.п.).
- **На хвосте после конца окна анализа** (5121 пара, 22 символа, медиана 13 дней):
  - доходность: INCOME лучше в 53% структур, без устойчивого отличия;
  - просадка: у INCOME выше в 75–85% структур;
  - убытки: одинаковые;
  - отношение доходности к просадке: INCOME лучше в 41% структур.

Преимущество INCOME на всём окне объясняется подгонкой весов под тот же период. Вне выборки его нет. Кроме того, INCOME закрепляет приоритет мелкого ордера, от которого отбор зон v4 отказывается.

## Decision

1. Генерация стратегий MRS3 (READY, fresh analysis, legacy pipeline) выпускает только вариант `EQUAL`.
2. Тик-тесты MRS3 и оценочные прогоны идут только по `EQUAL`. Количество тик-тестов на структуру сокращается вдвое.
3. Риском стратегии управляет масштаб всей стратегии (DD5 / потолок риска по просадке обучения), а не перераспределение лотов между ордерами.
4. Существующие результаты `INCOME` в PerformanceDB остаются читаемыми. Тип `LotMethod.INCOME` и правила дедупа ADR-0023 сохраняются для исторических данных; новых `INCOME` не создаётся.

## Consequences

- Нужна отдельная спецификация и TDD-реализация. Места, которые сейчас требуют пару `EQUAL` + `INCOME`:
  - `src/mrs3/analysis_strategies.py` (выбор методов при публикации);
  - `src/mrs3/fresh_analysis_strategies.py` (генерация для свежего прогона);
  - `src/mrs3/pipeline.py` (`add_variant` и проверка «ровно EQUAL и INCOME»);
  - `src/mrs3/strategy_json.py` (ожидаемые имена по всем `LotMethod`);
  - `src/mrs3/performance_v2_selection.py` (выбор победителя между вариантами лотов, `LOT_VARIANT_*`).
- Отбор Performance v2 должен корректно работать с одиночным `EQUAL` без пары `INCOME`.
- Метка способа лотов теряет смысл и убирается из новых данных: суффикс `_EQUAL` в имени стратегии, колонка `Lot mode` в XLSX, фильтр выбора варианта лотов. Исторические имена с суффиксом остаются читаемыми. Новые имена без суффикса не должны ломать связь READY JSON ↔ отчёт тестера ↔ PerformanceDB и дедуп по конфигурации (ADR-0023) — это проверяется в спецификации реализации.
- Проверка повторяется на новых данных (ноябрь 2026): хвосты вне выборки были короткими, а структуры построены старым продакшен-отбором.
