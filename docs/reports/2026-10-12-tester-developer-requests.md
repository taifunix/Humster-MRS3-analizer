# Просьбы и вопросы к разработчику тестера (2026-10-12)

Сводный список для передачи разработчику. Решения за ним; наш анализ от
ответов не блокируется. Вопросы по Portfolio Tester и торговому боту —
отдельно: [вопросы по портфельному тестеру](../superpowers/plans/Portfolio-Optimizer/07_DEVELOPER_QUESTIONS_AND_TESTER_WISHES_RU.md).

**Контекст.** Анализ одиночных стратегий (MRS2) теперь строится только из
`reports_history.csv` и `run_snapshot_*.json`, без HTML. Готовые
многоордерные стратегии (MRS3) мы пока разбираем из HTML: только там есть
эквити и действия. Цель — получать всё нужное в машиночитаемом виде и
перестать разбирать HTML совсем.

## 1. Колонки `reports_history.csv`

1. **Точность.** `MaxDrawdownPercent` и `WinRate` сейчас с 2 знаками. Нужно
   хотя бы 4–6: пороги по просадке и пограничные случаи зависят от округления.
2. **MAE.** Добавить колонки по метрикам, которые сейчас есть только в HTML,
   включаемые флагами в секции `reports_history` конфига, как `ulcer_index`:
   - `AvgMAE` и `WorstMAE` — средний по сделкам худший открытый PnL и худший
     из них. В HTML
     они в USDT («Avg MAE (worst open PnL)», «Worst MAE»); просим и USDT, и
     % кошелька на момент входа, чтобы сравнивать прогоны с разным балансом;
   - `MaxUnrealizedDDPercent` — максимальный нереализованный убыток, %
     кошелька (в HTML: «Max Unrealized Drawdown, % of wallet»).
3. **Настройки в одиночном прогоне.** Колонки `settings[*]` (символ, TF,
   параметры MA) появляются только у перебираемых параметров. В одиночном
   прогоне их нет совсем, и такой CSV нельзя разобрать без снимка настроек.
   Просим всегда выводить символ, TF и параметры MA каждой стороны.

## 2. Вопросы по определениям метрик CSV

1. **`MonthlyReturn_ГГГГ_ММ`.** В % от баланса на начало месяца или от
   стартового? Как считаются неполные первый и последний месяцы? Почему при
   `EndDate = 2026-10-01 00:00` в октябре стоит 0,01?
2. **`UlcerIndex` (hourly).** По какому ряду считается (Margin balance =
   кошелёк + нереализованный PnL?) и в процентах от чего?
3. **Monte Carlo** (`MC_MaxDD_p95`, `MC_LossProbability`). Это bootstrap
   сделок с возвратом или перестановка? При перестановке вероятность убытка у
   прибыльной стратегии всегда 0. Сколько времени добавляют 1000 итераций на
   прогон при переборе в тысячи прогонов? Есть ли минимальное число сделок?
4. **Режимы рынка.** ATR(14) для «высокой волатильности» считается по барам
   стратегии или по дневным барам? Если по барам стратегии, режим зависит от
   её таймфрейма.

## 3. Машиночитаемый вывод вместо HTML

Просим на каждый прогон, рядом с HTML, файлы в Parquet (или CSV):

1. **Метаданные прогона:** версия тестера; полный JSON стратегии; период;
   стартовый баланс; режим и база сайзинга; комиссии; биржа; параметры
   инструмента (`lotSize`, минимальный ордер).
2. **Действия:** всё, что есть сейчас в HTML (время, действие, `order_id`,
   размер, позиция после, PnL, комиссия, баланс, цена, номинал). Дополнительно:
   какой ордер стратегии (уровень MA) и запрошенное количество против
   исполненного.
3. **Эквити барами фиксированного шага** (например, 1 ч):
   - эквити open/high/low/close, где high и low взяты с самого точного
     разрешения тестера;
   - кошелёк на close;
   - худший нереализованный PnL в баре;
   - номинал позиции на close;
   - база сайзинга.

   По high и low просадка считается точно на любом шаге, а объём — около
   9 тыс. строк на стратегию в год. Из этого ряда мы сами считаем Ulcer, время
   под водой, хвостовой риск и средний за день худший плавающий убыток.
4. **Аналитические метрики HTML** колонками, а не только текстом отчёта
   (просадки по эпизодам, MAE, PnL по режимам рынка, Buy & Hold, фандинг).

Сейчас HTML нового формата наш строгий парсер уже не читает: метрики
повторяются, в таблицах объединённые ячейки. Машиночитаемый вывод снимет эту
зависимость.
