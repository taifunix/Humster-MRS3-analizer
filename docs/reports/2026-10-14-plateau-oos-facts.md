## 3. Метод

### 3.1 Обучение

Разрезы: T = начало READY + 42 + 14·i дней, пока помещается хотя бы F = 14.

- S = начало READY — основной вариант (`exp`).
- S = max(начало READY, T − 56 дней) — вариант чувствительности (`roll`).
  Где он совпадает с `exp`, используются те же стадии.

Строки обучения строятся так же, как в продакшене: `calculate_metrics` на
[S, T), затем `analysis_input_row`, затем `_analysis_frame_row`, затем
`_analyze_points`. Пустые окна: `GENUINE_ZERO_ACTIVITY` и
`WINDOW_EXCLUDES_MEASURABLE_DATA` превращаются в flat. Любая другая ошибка
исключила бы скоуп на разрезе, но таких не было.

### 3.2 Прямое окно: что показала проверка в валюте

Прямые окна считаются по рядам полной истории (`calculate_metrics(fragments)`),
а не по оконному `calculate_metrics`. Проверка в валюте (§5.5, п. 6) выявила
вот что.

- **Фандинг не хранится отдельными событиями.** Он зашит в `action.balance`.
  Фандинг действия = `balance_i − balance_{i−1} − (pnl_i − fee_i)`.
- **Замеры баланса (wallet samples) — точная, но разреженная копия цепочки
  `action.balance`.** Каждый замер равен цепочке в свой момент; у 12% точек
  встречаются копеечные (10⁻⁴–10⁻³ в валюте) расхождения внутри одной
  миллисекунды с действием. Но закрывающее действие может долго оставаться без
  замера: на 1h/4h до 26 суток. Поэтому «последний замер строго до T»
  устаревает. Реализованный PnL сделок, закрытых перед T, тогда переезжает в
  прямое окно, а закрытых перед T+F — из него выпадает.

| Проверка | F = 14 | F = 28 |
| --- | --- | --- |
| Покрытые прямые окна | 778 939 | 452 886 |
| Δбаланса по цепочке = Σ(pnl − fee + фандинг) | 100% (макс. 2·10⁻¹³) | 100% |
| Δбаланса по замерам = та же сумма | 70,3% окон | 65,4% окон |
| Максимальное расхождение «по замерам», валюта | 250 | 247 |
| Якорь «по замерам» отличается от цепочки | 18,9% окон | 20,6% окон |

Независимая проверка по заголовку отчёта тестера, 606 390 точек полной
истории:

| Итог | Совпадает до 0,011 |
| --- | --- |
| Σ fee = `Total fees` | 100% |
| Σ pnl > 0 = `Gross profit`, Σ pnl < 0 = `Gross loss` | 100% |
| Фандинг по цепочке = `Funding net` | 99,4% |
| Последний баланс цепочки = `Final balance` | 99,4% |

Все расхождения по `Funding net` и `Final balance`, кроме 25 точек, — у 4 066
точек с позицией, открытой в конце отчёта. Её закрытие тестером на конце
отчёта лежит за отрезкой хвоста и в окна исследования не попадает.

**Решение для исходов (основной вариант).**

- Баланс в момент x — по цепочке действий до x.
- Эквити-путь — замеры эквити плюс моменты, где действие оставляет позицию
  пустой (там эквити = баланс).
- Якоря — строго до T. Просадка — от бегущего пика, который стартует с
  эквити-якоря, в % от пика (как `_drawdown_details`).
- `DD_train` для исходов считается тем же способом на [S, T). Продакшен
  `dd_pct` используется только в обучающем анализе и в признаках отбора.

Колонки `*_samples` в `forward_points` и `outcomes` дают тот же расчёт
буквально по замерам. На итоговых долях разница мала: Success_10 по корзинам
шифта совпадает до 0,001.

Покрытие окна: история доходит до T+F, фрагмент сшит
(`full.period_metrics`), и отрезка открытого хвоста не раньше T+F.
Непокрытое окно исключается.

**Факт о продакшене (вне задачи, для сведения).** `calculate_metrics` по полной
истории даёт `total_pnl`, не равный `Total PnL` тестера, у **13 139 точек без
открытого хвоста (2,2%)**: медиана 0,5, максимум 14,8 в валюте при базе ~100.
Причина та же: последнее закрытие не попало в замеры баланса. Под-окна
(обучение, PRETEST B) анкерятся на замеры и подвержены тому же. Обучающий
анализ этого исследования намеренно повторяет продакшен вместе с этой
особенностью.

### 3.3 Позиция, открытая в момент T

В оконном `calculate_metrics` PnL окна отсчитывается от первого замера
баланса внутри окна. Сделки же отбираются по времени действий: закрытие внутри
окна без входа становится orphan round trip.

В расчёте по полной истории сделка, открытая до T и закрытая в окне, входит в
`PnL_fwd` целиком. Её число и валовый PnL выгружены
(`crossing_trades` / `crossing_gross_pnl`). Позиция, открытая на T+F, входит в
`DD_fwd` нереализованным PnL и не входит в `PnL_fwd` (`open_positions_at_end`,
`upnl_at_end`).

| Корзина шифта, F = 28 | Есть сделка через T | Открыта позиция на T+F | Нереализованный убыток на T+F |
| --- | --- | --- | --- |
| 30–70 | 34,3% | 25,1% | 19,3% |
| 90–200 | 19,2% | 12,8% | 9,7% |
| 230–390 | 10,5% | 6,2% | 4,3% |
| 430–550 | 7,4% | 3,4% | 1,9% |

### 3.4 Исходы, оценки, методы и статистика

Исходы — по §2 промпта. R = PnL_fwd × (30/F) × 5 / max(DD_train, 1).
Breach = DD_fwd > DD_train. Breach_F — то же против максимума просадки на
скользящих F-дневных отрезках обучения. Success_k = R ≥ k и не Breach.
Bad = PnL_fwd ≤ 0 или Breach. Отсутствие сделок в прямом окне — это PnL 0,
доля показывается отдельно.

Оценки окрестности 3 × 3 × 3 (S_min, S_q25, S_pool) — ровно три
предрегистрированных варианта по продакшен-метрикам обучения:

- непрошедшие соседи участвуют своими значениями;
- сосед с DD = 0 даёт неопределённый DD5/30 и в S_min/S_q25 пропускается;
- для точки с собственным DD = 0 оценки не определены. На обучении `exp` это
  46 492 точки, почти все на шифтах ≥ 230.

Методы M0–M5 — по таблице §5.6, все внутри одного (скоуп, разрез, вариант).

- k = |M1|; если M1 пуст — k = 4 (флаг `M1_EMPTY_K4`).
- Выбор продакшена для M5: `base_1ord_point_id`, иначе представитель
  `PRIMARY_CLOSE`.
- M5c — вторичное сравнение по каждой паре (плато, CloseMA).

Статистика:

- Бутстрэп по символам, 2 000 повторов.
- Парные разницы считаются внутри скоупа-разреза, усредняются по символу, затем
  берётся среднее по символам.
- p двусторонний по бутстрэпу. Поправка Холма — на шесть основных сравнений.
- Спирмен — внутри скоупа-разреза (≥ 8 точек, прошедших экономику). Берётся
  медиана по скоупам, ДИ — бутстрэпом по символам (500 повторов).
- Половины символов: хэш SHA-256 символа, разбиение зафиксировано до расчётов.
  Исследовательских вариантов, придуманных по ходу, нет; половины показаны как
  проверка устойчивости.

### 4.8 H6: многоордерные структуры (этап 2)

Приближение MRS3 — сумма рядов одиночных точек с равными лотами. Баланс
структуры — сумма цепочек баланса её ордеров. Эквити — сумма последних
известных эквити ордеров в каждой метке объединённого пути. Якоря, окна и
просадка — как в §3.2; DD_train — на [S, T) по той же суммарной кривой.

Сравниваются два вида структур:

- **PROD** — все текущие `structures` обучающего анализа (exp).
- **M4S** — предрегистрированное правило из точек, прошедших экономику, с
  определённым S_min. На каждую CloseMA точки перебираются жадно по
  убыванию S_min. Точка добавляется, только если вместе с уже выбранными
  шифты строго растут, каждый соседний гэп ≥ `required_gap_bp`, а окрестности
  3 × 3 × 3 попарно не пересекаются (разница индекса шифта ≥ 3 или OpenMA ≥ 3).
  Ордеров не больше `max_orders`, структура сохраняется при ≥ 2 ордерах.
  `validate_order_tuple` целиком не применялся: вне плато он требует разные
  `plateau_id` и флаги допуска, которые там ложны. Флаг допуска первого ордера
  в M4S не требуется (в PROD требуется).

## 5. Предварительные наблюдения

Это не выводы: проверка и окончательная интерпретация — за локальной сессией.

1. Эффект отбора на основной конечной точке малый и неустойчивый. Ни одно
   сравнение не проходит поправку Холма. Медиана по символам — 0. Эффект
   сосредоточен на нескольких T и в одной половине символов.
2. Отбор по оценкам окрестности (M4q, M4min) поднимает Success_10 примерно
   настолько же, насколько топ по PnL/DD (M3e) — на 3–5 п.п. Но поднимает и
   Breach/Bad. M3e повышает Bad сильнее всех (+9 п.п.). Рост «успеха» здесь
   идёт вместе с ростом риска превысить обучающую просадку.
3. Плато как фильтр почти не работает: в него попадают 98% прошедших
   экономику точек. Видимое преимущество членов плато над изолированными —
   в основном меньший Breach (−4,9 п.п.).
4. Текущий выбор точки внутри плато (продакшен) и «центр по S_min» дают
   одинаковые доли успеха. У центра чуть выше Breach.
5. В этом периоде мелкие шифты по самой точке — лучшие по Success_10 и Bad.
   Глубокие шифты почти не достигают R ≥ 10 и часто не торгуют в прямом окне.
   Ни один признак обучения их будущее не предсказывает. Посылка H4 («мелкий
   шифт не лучше») этими данными как одиночная точка не поддержана.
   Роль глубоких шифтов как усредняющих ордеров — это вопрос этапа 2 (§4.8).
6. Внутри корзины 90–200 высокий S_q25 связан с более низким Success_10 и
   более высоким Bad. В 30–70 — наоборот. Квартиль считается по всему скоупу,
   поэтому в разных корзинах он означает разное. Это требует отдельной проверки.
7. Структуры из точек с высокой оценкой окрестности (M4S) в общих долях
   выглядят лучше текущих `structures`, но внутри одних и тех же
   скоуп-разрезов не отличаются. Видимая разница — состав выборки. Текущий
   алгоритм порождает десятки и сотни структур на скоуп-разрез (медиана 77,5);
   M4S — до 6. Трёхордерные структуры в приближении хуже двухордерных у обоих
   видов.

## 6. Ограничения

- Все символы — один рыночный период, июнь–сентябрь 2026. T сгруппированы в
  несколько календарных дат, на 08-21 … 09-04 приходится большинство символов.
- F = 28 есть только у 43 символов (READY ≥ 70 дней). Основные сравнения
  опираются на 33–38 символов.
- Прямые окна и DD_train для исходов считаются по цепочке действий, а не по
  замерам (§3.2). Эквити между замерами не наблюдается; внутриинтервальная
  просадка может быть занижена так же, как в продакшене.
- R тяжелохвостый, поэтому сравнения ведутся по долям. Механическая связь
  DD_train с R и Breach описана в §4.5.
- Окрестность использует продакшен-метрики обучения. Они подвержены той же
  разреженности замеров (§3.2, факт о продакшене).
- Этап 2 — приближение суммой кривых с равными лотами (§4.8).
- Отчёт 2026-10-12 и `scripts/mrs2_research/`, на которые ссылается промпт,
  отсутствуют в репозитории (ни в одной ветке). Сравнение со стилем и выводами
  того отчёта не делалось.
- Профиль анализа — пользовательский `config.local.json`; он отличается от
  профиля в промпте (§2.5).
- Сверка с базами анализа — не здесь, а в локальной сессии.

## 8. Пакет выгрузки

Папка `plateau-oos-export-2026-10-14/` вне репозитория: 18 parquet-файлов (zstd) и `manifest.json`, всего **1 180.2 МБ**. Таблица больше 450 МБ режется на части `<имя>.partNN.parquet` (сейчас только `daily_equity`, 3 части). Части проверены: сумма строк и число уникальных строк совпадают с исходником. Внутри нет локальных путей (проверены все текстовые колонки), только имена файлов баз.
