# Выбор PerformanceDB и профиль биржи в Panel (P7)

**Статус:** утверждена пользователем 2026-10-13; реализована (P7a–P7d, 2026-10-13).
**Зависит от:** [протокол оценки MRS3 v2](2026-10-12-mrs3-evaluation-protocol-v2.md)
§4.1 (база на биржу, маркеры), §4.2 (рендер ставит `exchange.name` активной
базы), §7a (карта P6).

## 1. Цель

Пользователь тестирует MRS3 параллельно на двух биржах (Bybit и BingX), под
каждую биржу — своя PerformanceDB с маркером `schema_info.exchange`
(решение 2026-10-12). Panel должна:

- показывать базы PerformanceDB и выбирать активную без правки файлов вручную;
- создавать новую базу протокола v2 для выбранной биржи;
- рендерить оценочные тесты с параметрами активной биржи (профиль биржи), чтобы
  один глобальный шаблон стратегии и один шаблон тестера работали для обеих бирж.

## 2. Не входит

- Данные оптимизатора для второй биржи: справочник маржи (IM/MM, риск-лимиты,
  параметры инструмента — с API биржи), минутная ликвидность (папка рядом с
  папкой Bybit, имя `BingX`). Это отдельная фича. До неё Stage 1/2 для базы не
  Bybit отказывают `EXCHANGE_DATA_UNAVAILABLE`, а не считают по правилам Bybit.
- Спред-скрин и сбор спредов (заморожены).
- Перенос или слияние данных между базами.
- Сопоставление тикеров BingX (`NCSKTSLA2USD-USDT` ↔ `TSLAUSDT`) и пофандинговые
  интервалы отдельных пар: тестер принимает один `FundingIntervalHours` на запуск.

## 3. Хранение (решение пользователя: `config.local.json`)

- `config.performance.json` (в репозитории) остаётся источником настроек отбора и
  базы по умолчанию. Panel его не переписывает.
- Локальный `config.local.json` получает раздел `performance_databases`:

  ```json
  "performance_databases": {
    "active": "bybit-v2",
    "items": {
      "bybit-v2": {"database_root": "data/performance-v2-bybit", "exchange": "Bybit"},
      "bingx-v2": {"database_root": "data/performance-v2-bingx", "exchange": "BingX"}
    }
  }
  ```

  `evaluation_protocol` записи по умолчанию `v2`; `v1` допустим, чтобы
  зарегистрировать текущую базу. Активная запись переопределяет
  `database_root`, `evaluation_protocol` и `exchange` из
  `config.performance.json` в `load_performance_v2_config`, поэтому Panel и
  скрипты видят одну и ту же активную базу. `active` отсутствует или `null` —
  база из `config.performance.json` (так же возвращаются к ней); `active` без
  записи — `PERFORMANCE_DATABASE_UNKNOWN`. Без раздела всё работает как сейчас.
- `database_root` записи: относительный путь (те же лексические правила, что в
  `config.performance.json`), после `resolve()` остаётся внутри проекта
  (защита от junction); корни записей попарно различны и не вложены друг в
  друга; корень записи может совпасть с корнем базы по умолчанию (регистрация
  текущей базы), но не быть вложен в него или содержать его; проверка пересечения с v1-корнем при открытии базы не меняется.
- Тот же файл получает `exchange_profiles.<биржа>` (ключ сравнивается с
  маркером биржи без учёта регистра):

  | Поле | Допустимые ключи | Куда идёт при рендере |
  | --- | --- | --- |
  | `strategy_exchange` | `account`, `subaccount_name`, `account_type`, `bybit_transfer_profit` | блок `exchange` каждой стратегии |
  | `tester` | `MakerFee`, `TakerFee`, `FundingRate`, `FundingIntervalHours`, `SlippagePercent` | конфиг тестера каждого запуска и RUNS |
  | `listing_dates` | `path`, `sheet` | обрезка прогрева при импорте и границы RETEST |

  Неуказанные поля берутся из шаблонов. `exchange.name` стратегии всегда равен
  маркеру биржи активной базы (протокол §4.2), поэтому его нет в профиле. Ключ
  профиля сравнивается с маркером после `strip()` и без учёта регистра; два
  ключа одной биржи — `EXCHANGE_PROFILE_INVALID`. Профиль загружается отдельно
  от `PerformanceV2Config` и передаётся в `evaluation_target(config,
  tester_template, profile)`.
- Шаблоны стратегии и тестера — профиль Bybit. Для биржи `Bybit` профиль
  необязателен; для другой биржи без профиля рендер и запуск отказывают
  `EXCHANGE_PROFILE_MISSING`, чтобы не тестировать на комиссиях Bybit.

### 3.1. Профиль BingX (значения от 2026-10-13)

Публичный API BingX (`/openApi/swap/v2/quote/contracts`, `premiumIndex`):
у всех 189 найденных пар листа `Пары_BingX` базовые комиссии maker 0,02%,
taker 0,05%; интервал фандинга 8 ч у 177 пар (у 12 — 4 ч или 1 ч).

| Поле | Значение | Источник |
| --- | --- | --- |
| `MakerFee` | `0.00012` | 0,0002 × (1 − 40%) — индивидуальная скидка пользователя |
| `TakerFee` | `0.0003` | 0,0005 × (1 − 40%) |
| `FundingRate` | как у Bybit (`0.00025`) | решение пользователя |
| `FundingIntervalHours` | `8` | API BingX, основная масса пар |
| `SlippagePercent` | из шаблона | работа лимитками, не влияет |
| `strategy_exchange.account` | `bingx` | решение пользователя |
| `strategy_exchange.account_type` | не задан — наследуется `UNIFIED` шаблона | проверяется первым запуском бота |
| `listing_dates` | `input/bybit_tradfi_liquidity.xlsx`, лист `Пары_BingX` | решение пользователя |

Ставка со скидкой задаётся в профиле, а не берётся из API: публичный API
отдаёт базовую ставку. Точное имя биржи, которое ожидает бот для BingX, проверяется
первым запуском; маркер биржи базы должен совпадать с ним.

## 4. Рендер и предикат

- `EvaluationTarget` несёт поля профиля: `tester` и `strategy_exchange`.
  Без профиля они пусты, и рендер для Bybit не меняется.
- Рендер (§7a протокола) ставит в стратегию поля `strategy_exchange` профиля;
  `my_fix_balance` и `exchange.name` — как раньше.
- Конфиг тестера: Panel передаёт генераторам эффективный шаблон — шаблон
  тестера с полями `tester` профиля. Без полей `tester` передаётся сам шаблон;
  иначе — производный файл в `results/.tester-templates/` (каталог
  игнорируется git) с именем по SHA-256 содержимого. Файл неизменяем и
  создаётся заново при каждом рендере, если его удалили. Эффективный шаблон
  заменяет `mrs3_tester_config_template(self.root)` во всех местах Panel:
  публикация RUNS (`tester_config` снимка берётся из него, поэтому RUNS получает
  поля профиля), пакетный и одиночный тестер (Panel ставит шаблон в сервис перед
  `start`/`retry`), проверка шаблона перед запуском. Базу B по-прежнему даёт
  `InitialBalance` исходного шаблона.
- Предикат §4.2 дополняется: поля `tester` профиля равны в конфиге тестера
  (`PROTOCOL_V2_TESTER_CONFIG_REJECTED` с перечнем), поля `strategy_exchange`
  равны в стратегии (`PROTOCOL_V2_RENDER_REJECTED`). Протокол §4.2 («рендер
  ничего не подменяет, кроме двух полей») расширяется этим разделом: рендер
  ставит ещё поля `strategy_exchange` профиля.
- Маркер задания (протокол §7a) дополняется `evaluation_database` (папка
  активной базы относительно проекта) и `evaluation_profile` (SHA-256
  канонического JSON полей `tester`, `strategy_exchange`, пути и листа дат
  листинга).
  Повтор и переиспользование RETEST требуют совпадения всех полей маркера, иначе
  `RETRY_PRE_PROTOCOL_V2`; поэтому после смены базы или профиля старое задание
  запускается заново, а не импортируется в другую базу. Импорт задания с
  маркером v2, не совпадающим с текущей целью, отказывает
  `IMPORT_TARGET_CHANGED`; задания без маркера (v1) импортируются как раньше. Принятое исключение из
  инварианта 1: задания, отрендеренные до P7 (без этих полей), не повторяются и
  не переиспользуются — их запускают заново. На практике таких заданий нет:
  P6 рендерит только для v2-базы, а рабочая база пока v1.
- Дайджест конфигурации финалистов включает `strategy_exchange`, поля `tester`
  и лист дат листинга, когда они заданы; без профиля дайджест прежний.
- Даты листинга: `listing_dates` профиля заменяет `panel_workflow.listing_dates_path`
  для RETEST, отбора финалистов и импорта. Лист `sheet` читается с колонками
  `Пара` и `Листинг` (или `Дата листинга на Bybit (UTC)`); без `sheet` загрузчик
  работает как сейчас; `sheet` для CSV — ошибка. Задание RETEST сохраняет лист
  в runtime рядом с путём. Анализ Stage 1/2 и READY JSON по-прежнему берут
  `panel_workflow.listing_dates_path`: это данные Bybit, а для базы не Bybit
  Stage 1/2 отказывают (P7d).
- Импорт отклоняет отчёт чужой биржи (`EXCHANGE_MISMATCH`, без изменений).

## 5. Panel: раздел настроек «PerformanceDB»

- Список баз из `performance_databases` и база из `config.performance.json`:
  имя, папка, протокол, биржа, маркеры файла, размер, признак «активна».
- «Сделать активной»: только когда в журнале Panel нет незавершённых заданий,
  включая сбор отчётов и импорт (`RESOURCE_BUSY`). Переключение переписывает
  только `performance_databases.active` (`null` — база по умолчанию).
- «Создать базу»: имя, папка (относительная, внутри `data/`, не занятая) и
  биржа; база создаётся пустой, протокол v2, маркеры записываются при создании;
  запись добавляется в `performance_databases`.
- Профили бирж показываются в том же разделе; правка профиля — в
  `config.local.json` (UI-редактор профиля — вне P7).
- Запись `config.local.json` атомарная (временный файл + замена), остальные
  разделы файла сохраняются.

## 6. Этапы

- **P7a** — эта спецификация.
- **P7b** — переопределение активной базой, профили бирж, рендер и предикат с
  профилем, даты листинга с листом.
- **P7c** — раздел настроек Panel (API и UI): список, переключение, создание.
- **P7d** — отказ Stage 1/2 `EXCHANGE_DATA_UNAVAILABLE` для базы не Bybit.

## 7. Инварианты

1. Без разделов `performance_databases` и `exchange_profiles` поведение Panel
   не меняется; рендер для Bybit даёт те же стратегии и конфиг тестера.
2. Panel никогда не открывает базу, чей маркер протокола или биржи расходится с
   активной записью (`EVALUATION_PROTOCOL_MISMATCH`, `EXCHANGE_MISMATCH`).
3. Переключение базы не трогает файлы баз; создание пишет только новую папку и
   запись в `config.local.json`.
4. Биржа не Bybit без профиля не рендерится и не запускается.

## 8. Acceptance evidence

- Тесты: переопределение конфига активной записью; создание базы с маркерами;
  отказ переключения при активных заданиях; рендер с профилем BingX (стратегия
  и конфиг тестера); предикат отклоняет конфиг тестера с чужими комиссиями;
  загрузка дат листинга с листа `Пары_BingX` и отказ `sheet` для CSV;
  `PERFORMANCE_DATABASE_UNKNOWN`, `EXCHANGE_PROFILE_MISSING`/`_INVALID`;
  проверки корней (вне проекта, вложенность, корень по умолчанию); отказ
  повтора и переиспользования RETEST при смене базы или профиля; дайджест
  финалистов меняется с профилем и прежний без него; отказ Stage 1/2
  `EXCHANGE_DATA_UNAVAILABLE` для базы не Bybit.
- Ручная проверка в Panel: создать базу BingX, переключиться, отрендерить READY
  JSON и проверить `exchange` и комиссии.
