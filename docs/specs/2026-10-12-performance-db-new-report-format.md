# PerformanceDB: импорт отчёта тестера нового формата и аналитика отчёта

Дата: 2026-10-12. Статус: **утверждено пользователем 2026-10-12** (список §3 и
требование совместимости §7). Реализуется в этой же ветке работ вместе с P2–P6
[протокола v2](2026-10-12-mrs3-evaluation-protocol-v2.md).

Связанные документы:
[протокол оценки v2](2026-10-12-mrs3-evaluation-protocol-v2.md) (схема v12, P2–P6),
[метрики нового отчёта](../reports/2026-10-12-tester-report-metrics-to-record.md),
[просьбы к разработчику тестера](../reports/2026-10-12-tester-developer-requests.md),
[оценка риска по эквити](2026-10-12-equity-risk-evaluation.md) (§10 — проверка на базе v2),
[обслуживание PerformanceDB](2026-10-06-performance-db-maintenance.md),
[lossless-сжатие](2026-09-30-performance-db-lossless-compaction.md).

## 1. Цель

1. Импорт Performance v2 читает HTML тестера нового формата (версия тестера
   не ниже `2026/10/10`), сохраняя прежний разбор старых отчётов.
2. База хранит утверждённый набор аналитики отчёта (§3) в типизированных
   таблицах, чтобы исследования и будущие фильтры брали её без повторного
   разбора HTML.
3. Старая база (протокол v1) остаётся полностью рабочей (§7).

## 2. Не входит

- Новые фильтры, ранжирование, колонки XLSX и Panel по этой аналитике — только
  отдельными спеками после проверки на накопленной базе v2.
- Разбор `reports_history.csv` и анализ MRS2 (CSV Direct).
- Машиночитаемый вывод тестера (Parquet) — ждёт ответа разработчика.
- Изменения отбора, ревью, оптимизатора и их выходов.
- Строгость v1 `performance_import.py` и Source v6: не меняется (§5.4).

## 3. Что берём из отчёта

Решения пользователя 2026-10-12: запасу до ликвидации не доверяем; загрузка
позиции — для оптимизатора; параметры инструмента — не аналитика; аналитику,
которую можно посчитать самим, храним ради сверки и будущих фильтров.

### 3.1 Одна строка на результат (`strategy_report_metrics`)

Единственный источник соответствия «метка отчёта → колонка» —
`REPORT_ANALYTICS_LABELS` в [performance_v2_html.py](../../src/mrs3/performance_v2_html.py)
(59 колонок; тип разбора — `decimal`, `integer`, `count_of`, `duration`,
`timestamp`). Группы:

| Группа | Колонки |
| --- | --- |
| Издержки | `gross_profit_usdt`, `gross_loss_usdt`, `trading_volume_usdt`, `funding_paid_usdt`, `funding_accrued_usdt`, `funding_net_usdt`, `net_costs_usdt`, `pnl_before_costs_usdt` |
| Концентрация прибыли | `top5_winning_pnl_usdt`, `pnl_without_top5_usdt` |
| MAE / MFE (USDT) | `avg_mae_usdt`, `avg_mae_winners_usdt`, `worst_mae_usdt`, `avg_mfe_usdt`, `profit_capture_winners_pct`, `losing_trades_in_profit` |
| Нереализованная просадка | `max_unrealized_dd_pct_wallet`, `max_unrealized_dd_usdt`, `max_unrealized_dd_at_utc` |
| Buy & Hold | `buy_hold_return_pct`, `excess_return_pct`, `buy_hold_max_dd_daily_pct` |
| Профиль сделок | `trades_full_exit`, `win_trades`, `loss_trades`, `expectancy_per_trade_usdt`, `avg_win_usdt`, `avg_loss_usdt`, `payoff_ratio`, `largest_win_usdt`, `largest_loss_usdt`, `avg_fills_per_trade`, `avg_holding_seconds`, `max_holding_seconds`, `max_consecutive_wins`, `max_consecutive_losses` |
| Исполнения | `fills_reduce_close`, `win_fills`, `loss_fills` |
| Аналитика тестера (для сверки) | `ulcer_index_hourly_pct`, `martin_ratio`, `time_under_water_pct`, `drawdown_episodes`, `longest_drawdown_seconds`, `var95_daily_pct`, `cvar95_daily_pct`, `worst_day_pct`, `best_day_pct`, `skewness`, `excess_kurtosis`, `sharpe_monthly`, `sortino_monthly`, `cagr_pct`, `calmar_ratio`, `recovery_factor`, `avg_monthly_return_geo_pct`, `avg_monthly_return_arith_pct`, `best_month_pct`, `worst_month_pct` |

Производные доли (Fees / Net costs / Top 5, % …) не храним: они считаются из
колонок. Значения в таблицах отчёта округлены для показа; сверка с нашими
расчётами допускает округление. Полноточный JSON `<!--hb-run-summary …-->` в
начале HTML — возможный будущий источник, сейчас не используется.

### 3.2 Таблицы

- `strategy_report_regimes` — строка на режим. Соответствие — `REPORT_REGIME_LABELS`:
  `Trend · High vol` → `TREND_HIGH_VOL`, `Trend · Low vol` → `TREND_LOW_VOL`,
  `Flat · High vol` → `FLAT_HIGH_VOL`, `Flat · Low vol` → `FLAT_LOW_VOL`,
  `Trend (all)` → `TREND`, `Flat (all)` → `FLAT`, `High vol (all)` →
  `HIGH_VOL`, `Low vol (all)` → `LOW_VOL`, `↗ Uptrend` → `UPTREND`,
  `↘ Downtrend` → `DOWNTREND`. Колонки: `pair_days`, `pnl_usdt`,
  `avg_pnl_per_pair_day_usdt`, `winning_days_pct`, `pnl_share_pct`.
  Строка-разделитель из одной объединённой ячейки («Totals by one dimension») и
  строки с неизвестной меткой пропускаются; строка другой неверной ширины
  отклоняет отчёт. Определение режима тестером (ATR(14) по
  барам стратегии или по дням) — открытый вопрос к разработчику.
- `strategy_report_monthly` — строка на месяц тепловой карты: `month` (первый
  день месяца), `return_pct`. Ячейка `—` строки не даёт; последняя колонка
  обязана быть `Year` (сложение месяцев) и не хранится; повтор строки года
  отклоняет отчёт. По подсказке отчёта база месяца —
  Margin balance на конец предыдущего месяца (первый месяц — от стартового
  баланса).

### 3.3 Идентичность отчёта (`strategy_results`)

- `tester_version` — `2026/10/10` (без префикса `ver.`), из `<span>` после
  `hb/tester/`; заполняется у любого отчёта, где версия есть, включая старые.
  Сравнение — как кортеж (год, месяц, день).
- `report_format` — `2026-10` или `legacy` для отчётов, импортированных после
  v12; у строк, импортированных до v12, — NULL. Читатели трактуют NULL и
  `legacy` одинаково.
- `exchange` (существующая колонка) по-прежнему берётся из `exchange.name`
  настроек отчёта. В отчётах нового тестера это имя биржи (`Bybit`); в старой
  базе у всех результатов `tester`. Привязка базы к бирже — маркер
  `schema_info.exchange` ([протокол v2 §4.1](2026-10-12-mrs3-evaluation-protocol-v2.md)).

### 3.4 Не берём

| Что | Почему |
| --- | --- |
| Запас до ликвидации, `liquidationSeries` | пользователь не доверяет расчёту |
| Position avg/max, в том числе Long/Short и CT/T, `positions*Series` | загрузка позиции — задача оптимизатора |
| Таблица инструмента (`maxMktOrderQty`, `leverage_max`, `lotSize`, объёмы) | параметры рынка, не аналитика стратегии |
| Таблица эпизодов просадок | считается из ряда эквити; храним число эпизодов и самый долгий |
| Часы суток, активность исполнений, таблицы по символу и стороне | для отбора не нужны; одна пара и одна сторона на результат |
| Monte Carlo (`MC_*`) | выключен по умолчанию; метод и цена — вопрос к разработчику |
| Колонки журнала действий Strategy, Side, `Cost, % of margin balance` | остаются в `raw_action_json`; `Price` и `Cost` уже разбираются |

## 4. Текущее состояние (проверено 2026-10-12)

- `parse_current_performance_v2_html` на образце нового формата падает с
  `metrics contain duplicate or empty keys`. Вторая блокировка — общая проверка
  ширины строк во всех таблицах: в таблице режимов есть строка
  `<td colspan="6">Totals by one dimension</td>`.
- Повторяются 11 меток. Расходятся три: `Largest win` (`0.0918` и
  `0.09 · ARKKUSDT · 2026-09-02 13:43`), `Largest loss` (`-0.1643` и
  `-0.16 · …`), `PnL without best pair` (`n/a` и `n/a (single pair)`).
- Отчёт тестера `ver.2026/09/22` уже содержит Report Statistics, Details,
  тепловую карту, колонки действий Strategy/Side/Cost и `positions*Series`;
  новыми в `2026/10/10` стали `liquidationSeries` и аналитические таблицы. Поэтому
  формат определяется только версией.
- Импорт пишет в ядро результата метки `Max Drawdown` и `Total Trades`
  ([performance_v2_import.py](../../src/mrs3/performance_v2_import.py)). В новом
  формате их нет: есть `Max Drawdown, USDT`, `Total Trades (entry → full exit)`
  (завершённые позиции) и `Fills (reduce / close)` (закрывающие исполнения).
  Старое `Total Trades` (6934 в отчёте `2026/09/22`) соответствует закрывающим
  исполнениям.
- Схема — v11; цепочка миграций `_migrate_schema_v3_to_v4` …
  `_migrate_schema_v10_to_v11` применяется при открытии. Таблицы сжатия и
  обслуживания перечислены явно.
- Образец: `<tester_runner.bot_root>/tester/report/_/_run_001_of_001_ARKKUSDT_15m_*.html`
  (`bot_root` — из `config.local.json`). В репозиторий не коммитится; тесты —
  на синтетических фикстурах.

## 5. Контракт разбора

1. **Формат** — только по версии `ver.YYYY/MM/DD`, стоящей после `hb/tester/`
   (между ними допускаются теги и пробелы). Нет версии → `legacy`. Версия ≥
   `2026/10/10` → `2026-10`. Несколько разных версий в одном отчёте → отказ,
   в том числе для `legacy`. Отчётов от сборок `2026/10/09` с новым макетом не
   известно; если появятся, они пойдут как `legacy` и будут отклонены на
   повторах — порог тогда снижается константой.
2. **Метки → колонки** — `REPORT_ANALYTICS_LABELS` и `REPORT_REGIME_LABELS`.
   Неизвестные метки и строки игнорируются.
3. **Повторы меток** (все таблицы Metric/Value, не только метки §3). Главным
   считается первое вхождение (Report Statistics). Повтор допустим, если:
   текст равен; оба значения начинаются с `n/a`; ведущее число повтора равно
   главному числу по значению при любой точности (`9.9` и `9.90`); или повтор
   менее точен и равен главному числу, округлённому до его точности (`0.0918`
   → `0.09 · SYMBOL · время`). Знак `%` в обоих значениях не учитывается
   (`8.69%` и `8.7%`). Ведущее число должно кончаться концом текста, пробелом,
   `%` или `·` (`4.83e5` — конфликт). Главное значение должно быть числом.
   Иначе отчёт отклоняется: `conflicting duplicate metric: <метка>`.
4. **Где ослабление.** В общем `parse_performance_report` флаг
   `report_format_2026_10` (по умолчанию выключен) включает правило 3 и
   пропуск таблиц, которые не являются ни Metric/Value, ни журналом действий.
   Для таблиц метрик и действий сохраняются все проверки и перекрёстная
   сверка с независимым токенизатором. Флаг включает только разбор
   Performance v2 для формата `2026-10`; v1 `performance_import.py` и Source v6
   остаются строгими.
5. **Значения.** `n/a` и любое значение, начинающееся с `n/a`
   (`n/a (single pair)`), `—`, `-`, пусто → NULL. Бесконечности и `nan`
   (`inf`, `∞`, `nan`) → NULL: короткий тест может дать бесконечное отношение,
   и это не повод отклонять отчёт. Проценты `0.09%` → `0.09`. Длительности
   `1d 22h 3m`, в том числе с хвостом `(ongoing)`, → секунды. `54 of 56
   (96.43%)` → 54. `2026-08-31 13:15` → UTC.
6. **Строгость.** Метки нет → NULL. Метка есть, значение не разбирается →
   отказ `REPORT_ANALYTICS_INVALID: <метка>`; для строки режима — `Regime
   <метка>`; для тепловой карты — `Monthly Returns Heatmap` (структура),
   `Monthly return <год>` (повтор года), `Monthly return <год> <месяц>`
   (значение). Отказ
   касается только этого отчёта (статус `REJECTED` в партии), как и прочие
   ошибки разбора.
7. **Ядро результата для `2026-10`.** `max_drawdown` ← `Max Drawdown, USDT`;
   `max_drawdown_pct` ← `Max Drawdown, %`; `total_trades` ← `Fills (reduce /
   close)`, чтобы колонка сохранила смысл «закрывающие исполнения» в старой и
   новой базе; завершённые позиции — `trades_full_exit` (§3.1). Остальные
   метки ядра (`Initial/Final balance`, `Total PnL`, `Total PnL, %`,
   `Total fees`, `Report range`, `Total transactions (buy/sell)`) не изменились.
8. **Протокол** отчёта и факты MA проверяются по
   [протоколу v2 §4.4](2026-10-12-mrs3-evaluation-protocol-v2.md); формат и
   протокол независимы.

## 6. Схема v12 (аддитивно, одной миграцией с P2 протокола v2)

- `strategy_results`: `tester_version VARCHAR`, `report_format VARCHAR`.
  DuckDB не умеет добавлять колонку с ограничением через `ALTER TABLE ADD
  COLUMN`, поэтому значение (`legacy`, `2026-10` или NULL) проверяет импорт.
- `strategy_report_metrics(result_id BIGINT PRIMARY KEY REFERENCES
  strategy_results(result_id), …)`: колонки §3.1, все nullable. Типы:
  денежные, процентные и отношения — `DOUBLE` (значения отчёта округлены, а
  отношения бывают очень большими); счётчики и секунды — `BIGINT`;
  `max_unrealized_dd_at_utc` — `TIMESTAMPTZ`. Строка пишется для каждого
  отчёта `2026-10`, даже если все колонки NULL; для `legacy` строки нет.
- `strategy_report_regimes(result_id BIGINT REFERENCES strategy_results,
  regime VARCHAR, pair_days BIGINT, pnl_usdt DOUBLE, avg_pnl_per_pair_day_usdt
  DOUBLE, winning_days_pct DOUBLE, pnl_share_pct DOUBLE, PRIMARY KEY (result_id,
  regime))`.
- `strategy_report_monthly(result_id BIGINT REFERENCES strategy_results,
  month DATE, return_pct DOUBLE, PRIMARY KEY (result_id, month))`.
- Пути записи: ADD вставляет; REPLACE (обновление результата на месте)
  удаляет строки трёх таблиц этого `result_id` и вставляет новые в той же
  транзакции; отчёт `legacy` при REPLACE оставляет таблицы пустыми и пишет
  `report_format = legacy`.
- Обслуживание (`performance_v2_maintenance.py`): классификация таблиц схемы
  v12, проверка сирот, удаление результата и отклонённых (`_REJECTED_TABLES`)
  включают три таблицы. Надгробие (retirement Rejected) удаляет строки трёх
  таблиц; `tester_version` и `report_format` остаются как идентичность.
- Сжатие (`performance_v2_compact.py`): три таблицы в списке копирования и
  проверки; ключи диапазонов — `result_id`, ключи порядка — PK таблицы.
- Все жёсткие проверки версии схемы (`"11"`, `range(6, 12)` и т. п.) — по
  списку протокола v2 §6.

## 7. Совместимость со старой базой (требование пользователя)

- **Миграция.** `_migrate_schema_v11_to_v12` встаёт в существующую цепочку и
  применяется при открытии к любой базе. Она аддитивная: новые колонки
  nullable, новые таблицы пустые, существующие строки не переписываются,
  маркер протокола не трогается.
- **Отсутствие аналитики — нормальное состояние.** В старой базе таблицы §3
  пусты, `tester_version` и `report_format` — NULL. Каждый читатель трактует
  это как «нет данных» и продолжает работу. Будущие спеки, использующие
  аналитику, обязаны определить поведение при её отсутствии.
- **Panel и инструменты** работают со старой базой как раньше: отбор, ревью,
  XLSX, публикации, оптимизатор, RETEST, обслуживание, удаление, сжатие,
  скрипты проверки и обрезки.
- **Формат и протокол независимы.** Отчёт `2026-10` с протоколом v1
  (`use_upnl=true`) импортируется в старую базу и получает аналитику.
- **Откат кода** на версию до v12 после миграции не поддерживается; перед
  первой миграцией рабочей базы — резервная копия.

## 8. Инварианты

1. Для отчёта `legacy` все колонки, существовавшие до v12, и строки действий
   и эквити совпадают с импортом до изменения. Единственный новый отказ на этом
   пути — несколько разных версий тестера в одном отчёте (§5.1).
2. Существующие выходы (отбор, ревью, XLSX, оптимизатор, кэши эквити) не
   меняются: они новые таблицы не читают, а пустые таблицы и NULL-колонки
   ошибок не вызывают.
3. Строки §3.1–§3.2 существуют только для `report_format = 2026-10`.
   Если импорт пересчитал ядро отчёта из оставшихся сделок (обрезка по
   прогреву листинга или исключённый незавершённый цикл в конце), аналитика
   отчёта не хранится: она описывает необрезанный период (уточнение
   2026-10-13). `tester_version` и
   `report_format` пишутся и в этом случае.
4. Отчёт атомарен: ядро и аналитика пишутся в одной транзакции или не пишутся.
5. Метрики отчёта не подменяют наши расчёты из эквити; они хранятся рядом.

## 9. Acceptance evidence

- **N1 (разбор):** синтетическая фикстура `tests/fixtures/performance/report_2026_10.html`
  — повторы меток (совместимые и конфликт), `n/a`, бесконечности,
  неразбираемое значение, строка-разделитель режимов, тепловая карта; старая
  фикстура — `legacy` без аналитики; общий парсер без флага по-прежнему
  отклоняет повторы. Реальный образец §4: разбор проходит, все 59 меток
  найдены, 10 режимов и 3 месяца.
- **N2–N3 (схема и импорт):** фикстурный тест «база v11 → миграция → ADD и
  REPLACE отчётов `legacy` и `2026-10`»: ядро (`max_drawdown`, `total_trades`
  из правила §5.7), три таблицы, атомарность, отказ одного отчёта без отмены
  партии.
- **Совместимость (§7):** фикстура базы v11 после миграции проходит
  существующие наборы отбора, ревью, публикации, XLSX, оптимизатора,
  обслуживания и сжатия. На копии рабочей базы до и после миграции для трёх
  пар совпадают строки `selection_results` (`auto_status`, `auto_rank`,
