# BingX Downloader исторических 1m данных — спецификация

**Статус:** согласовано с пользователем 2026-10-10; этапы 1 и 2 реализованы, пробный прогон тестера на данных BingX выполнен 2026-10-11. 2026-10-16: дни хранятся в parquet нового тестера (раздел «Формат дня (parquet тестера)»), прежний архив CSV сконвертирован встроенным конвертером тестера. Этап 1 — модуль-загрузчик в проекте с ручным запуском из `scripts\`; этап 2 — режим BingX в панели (СКРИНЕР 01 и RUNNER 01). Факты API BingX проверены публичными запросами 2026-10-10.

## Цель

Создать в проекте модуль-загрузчик под Windows, который скачивает исторические 1-минутные OHLCV-данные BingX для заданных тикеров и диапазона дат, преобразует их в дневные файлы минутных свечей тестера Hamster (parquet), и при следующих запусках корректно докачивает только новые или отсутствующие дни.

## Платформа и состав файлов

Целевая ОС: Windows.

Загрузчик — часть проекта, оформляется по принятой в проекте схеме:

- `src/mrs3/bingx_downloader.py` — ядро: загрузка данных, запись и проверка дневных parquet-файлов. Его вызывают и ручной запуск, и панель (этап 2).
- `scripts/download_bingx_data.py` — ручной запуск: читает настройки из `config.local.json` и вызывает ядро.
- `scripts/run_bingx_download.bat` — запуск двойным кликом.

Отдельного файла настроек (`pairs_and_dates.json`) и файла `.env` нет.

## Настройки

Настройки хранятся в принятом в проекте файле `config.local.json`, в новом блоке `bingx`:

```json
"bingx": {
  "start_date": "2026-06-13",
  "end_date": "2026-10-11",
  "pairs": ["PANW", "BABA", "TSLL"],
  "download_mode": "incremental"
}
```

Параметры:

- `start_date` — первый календарный день диапазона, включительно. Общий для всех пар; если пара залистована на BingX позже, дни до её листинга пропускаются (см. «День листинга и дни до листинга»).
- `end_date` — последний календарный день диапазона, включительно.
- `pairs` — обычные тикеры, например `PANW`, `BABA`, `TSLL`.
- `download_mode` — по умолчанию `incremental`; значение `overwrite` принудительно перекачивает весь указанный диапазон.

`start_date`, `end_date` и `pairs` используются только при ручном запуске. При запуске из панели (этап 2) пары и даты берутся из полей панели.

### Папка данных

Папка данных не задаётся отдельно: она вычисляется из корня тестера `tester_runner.bot_root`, который уже есть в `config.local.json`:

```text
<bot_root>\tester\data\bingx\
```

Внутри неё скрипт создаёт и использует структуру `<api_symbol>\...`. В Python-коде и `.bat` абсолютных путей к папке данных быть не должно.

## API-ключи BingX

Файла `.env` нет. Загрузчик — надстройка над тестером, который пока сам не умеет качать данные BingX, а ключи BingX уже хранятся в папке тестера:

```text
<bot_root>\settings_accounts\bingx.json
```

Имя файла совпадает с `exchange.account` в файле стратегии (`bingx`). Ключи берутся из полей `api_key` и `api_secret` (обычные строки, `is_encrypted: false`). Ключи не копируются в `config.local.json`, не выводятся в лог и не хранятся в коде.

Оба endpoint, используемых загрузчиком (список контрактов и свечи), публичные — проверено 2026-10-10 запросами без ключей. Поэтому ключи для скачивания не обязательны: если файла нет, скрипт работает без подписи и не завершается с ошибкой. Поддержка подписи остаётся для запросов, где она необходима.

## Определение внутренних API-тикеров BingX

Пользователь указывает обычный тикер, например:

```text
PANW
```

Скрипт сам получает список/метаданные контрактов BingX и определяет внутренний canonical API symbol.

Примеры:

```text
PANW
→ displayName: PANW-USDT
→ API symbol: NCSKPANW2USD-USDT
```

```text
BABA
→ displayName: BABA-USDT
→ API symbol: NCSKBABA2USD-USDT
```

Пользователь не должен вручную указывать внутренние названия BingX.

Источник метаданных — публичный endpoint:

```text
GET https://open-api.bingx.com/openApi/swap/v2/quote/contracts
```

Правило сопоставления:

- рассматриваются только TradFi-контракты BingX — `symbol` начинается с `NCSK` (акции/ETF), `NCSI` (индексы) или `NCCO` (сырьё); крипто- и forex-контракты (`NCFX`) исключены, чтобы тикер акции не попал на одноимённую криптомонету (например, `ON` → `NCSKON2USD-USDT`, а не крипто `ON-USDT`);
- контракт подходит, если `displayName` без пробелов равен `<TICKER>-USDT` или `<TICKER>US-USDT` (BingX добавляет `US`, когда имя занято криптой: `AMDUS-USDT`), либо `symbol` равен `NCSK<TICKER>2USD-USDT`;
- если тикер оканчивается на `STOCK` (так Bybit называет часть акций: `AMDSTOCKUSDT`) и по полному тикеру ничего не найдено, суффикс `STOCK` отбрасывается;
- API symbol берётся из поля `symbol` найденного контракта (например, `NCSKPANW2USD-USDT`);
- нормализованный тикер для имени файла дня — базовый тикер плюс `USDT` (например, `PANWUSDT`, `AMDSTOCK` → `AMDUSDT`);
- из того же контракта берётся `launchTime` (Unix ms) — момент листинга.

Проверено 2026-10-11 на всех 242 парах реестра Bybit: 212 найдены однозначно, 30 на BingX отсутствуют (в основном акции Гонконга/Китая и сырьё с другими именами).

Если тикер не найден или подходит больше одного контракта, скрипт выводит ошибку по этой паре и продолжает обработку остальных тикеров.

## Загрузка исторических данных

Для каждой найденной пары и каждого запрошенного дня скрипт скачивает исторические 1-минутные OHLCV-свечи BingX за соответствующий UTC-день.

За завершённый день приходит не больше 1440 свечей по 1 минуте. За минуты без сделок BingX свечу не отдаёт (проверено 2026-10-11: ALAB 2026-07-04 — 1394 свечи, CSCO 2026-07-04 — 1171; повторный запрос даёт тот же набор, свечей с нулевым объёмом нет). Такие минуты остаются пропусками в файле дня, как в Bybit-файлах тестера; свечи за них не выдумываются (ни нулями, ни копией предыдущей цены).

Если API BingX ограничивает количество свечей за один запрос, скрипт должен автоматически делать необходимое количество запросов, пока не будет собран весь день.

Источник свечей — публичный endpoint:

```text
GET https://open-api.bingx.com/openApi/swap/v3/quote/klines
    ?symbol=<api_symbol>&interval=1m&startTime=<day_start_ms>&endTime=<day_start_ms + 86399999>&limit=1440
```

Поля свечи в ответе: `time` (время открытия свечи, Unix ms, UTC), `open`, `high`, `low`, `close`, `volume`. В файле дня `time` записывается в колонку `timestamp`.

Числовые значения переводятся из десятичной строки BingX в double без промежуточного округления (см. «Формат дня (parquet тестера)»).

Свойства API, проверенные 2026-10-10:

- максимальный `limit` равен 1440; при большем значении BingX возвращает ошибку `code 109400`. Значит, один полный UTC-день — ровно один запрос;
- `startTime = 00:00:00.000 UTC` и `endTime = startTime + 86 399 999` возвращают все свечи дня с 00:00 до 23:59 (у ликвидных пар — 1440);
- свечи приходят по убыванию `time`, поэтому перед записью их обязательно сортировать по возрастанию;
- ошибка сообщается полем `code` в JSON-ответе: успешным считается только ответ с `code == 0`, проверки одного HTTP-статуса недостаточно;
- часть стоковых контрактов торгуется 24/7 (у ликвидных PANW, TSLL, BABA приходят все 1440 свечей, у малоликвидных — меньше, пропуски приходятся на минуты без сделок, чаще в первые дни после листинга и в выходные);
- часть стоковых контрактов торгуется только в часы американской биржи: XLP, BAC, SKUU, SPCH — 391 свеча в будни и 0 свечей в субботу и воскресенье (проверено 2026-10-11, повторный запрос даёт тот же ответ).

При сетевых ошибках и rate limit BingX используется ограниченное количество повторных попыток с увеличивающейся задержкой между запросами.

## День листинга и дни до листинга

Контракты листятся в разное время, а `start_date` общий для всех пар. Фактический `launchTime` (проверено 2026-10-10):

```text
PANW  NCSKPANW2USD-USDT  2026-06-11 10:00 UTC
TSLL  NCSKTSLL2USD-USDT  2026-07-20 11:40 UTC
BABA  NCSKBABA2USD-USDT  2026-08-04 09:30 UTC
```

Например, для BABA запрос за 2026-08-03 возвращает пустой список, а за день листинга есть только свечи с 09:30 до 23:59.

Правила:

- дни, целиком лежащие до UTC-дня листинга, не скачиваются, не считаются ошибкой и не создают файла;
- в день листинга свечи начинаются не раньше минуты, в которую попадает `launchTime` (для PANW 2026-06-11 — до 840 свечей);
- в остальные дни — не больше 1440 свечей; пропуски минут без сделок допустимы;
- день, за который BingX не вернул ни одной свечи (сделок не было — например, выходной у контракта, торгуемого только в часы биржи), — не ошибка: файл за этот день не создаётся, день учитывается в статистике как «день без сделок»;
- такие дни нигде не запоминаются: при каждой докачке и при проверке перед подготовкой файлов день без файла перепроверяется у BingX одним запросом; если сделки появились, день скачивается (в проверке — считается недостающим), поэтому случайный пустой ответ API не прячет данные;
- файл с одной шапкой без строк никогда не записывается и не считается валидным; повреждённый файл за день, по которому BingX теперь не отдаёт свечей, удаляется.

Что тестер принимает отсутствующий файл за день без сделок, подтверждено пробным прогоном 2026-10-11: скрининг XLP (12 выходных без файлов) дал 304 отчёта BingX со сделками во всех месяцах и без ошибок в логе тестера.

Без этих правил дни до листинга и день листинга никогда не прошли бы проверку и перекачивались бы при каждом запуске.

## Структура папок и имена файлов

Каждая пара хранится в своей подпапке внутри папки данных `<bot_root>\tester\data\bingx\`.

**Название папки должно полностью совпадать с точным внутренним API symbol BingX.**

Пример:

```text
<bot_root>\tester\data\bingx\
├── NCSKPANW2USD-USDT\
│   ├── PANWUSDT2026-06-13_1m.parquet
│   ├── PANWUSDT2026-06-14_1m.parquet
│   └── ...
│
└── NCSKBABA2USD-USDT\
    ├── BABAUSDT2026-08-04_1m.parquet
    └── ...
```

Правило именования:

```text
папка = точный BingX API symbol           пример: NCSKPANW2USD-USDT
файл  = нормализованный тикер для Hamster  пример: PANWUSDT2026-06-13_1m.parquet
```

Внутренний BingX API symbol не используется в имени самого файла. Имя то же,
что было у CSV, только с расширением `.parquet`: так его пишет встроенный
конвертер тестера (`hb_c.exe --convert-data`).

## Формат дня (parquet тестера)

**Решение 2026-10-16.** Новый тестер читает минутные свечи только из parquet.
Источник истины по формату — встроенный конвертер тестера
`hb_c.exe --convert-data` (Parquet.Net): загрузчик пишет ровно то, что конвертер
получил бы из прежнего CSV BingX. Проверено 2026-10-16: конвертер сконвертировал
все 22 455 CSV-дней BingX (197 пар) без ошибок и построчно один в один
(30 401 707 строк); так же он переносит MEXC (`buy = sell = 0`, `trades = 1`,
минуты с нулевым объёмом) и Bybit.

Формат (общий модуль `src/mrs3/tester_candles.py`, тот же, что у
`portfolio/minute_capacity.py`):

- колонки в этом порядке: `timestamp` INT64 (начало минуты, мс UTC), `open`,
  `high`, `low`, `close`, `volume`, `buy_volume`, `sell_volume` DOUBLE,
  `trades` INT32;
- все колонки REQUIRED (не nullable);
- сжатие ZSTD у всех колонок;
- в key-value метаданных файла ровно одна запись `hb.schema = candles_1m/1`,
  без `ARROW:schema`;
- числа — десятичные строки BingX, разобранные в ближайший double (как
  `double.Parse` конвертера), без промежуточного округления.

Семантика колонок (как у прежнего CSV и после конвертера тестера):

- `buy_volume`, `sell_volume` и `trades` BingX не отдаёт (ни в свечах, ни в
  истории сделок — `historicalTrades` возвращает только последние ~1000 сделок).
  Во всех строках они равны `0`. Объём на buy/sell не делится, `trades` не
  выдумывается: конвертер тестера переносит такие значения как есть, и тестер
  их принимает;
- `volume` — **base asset volume**, который отдаёт BingX (для PANW — количество
  PANW, а не USDT); `volume × price` и пересчёт в USDT запрещены;
- строки — свечи, которые вернул BingX, по возрастанию `timestamp`; минуты, за
  которые BingX свечи не вернул, остаются пропуском; свечи с нулевым объёмом
  сохраняются, как у конвертера тестера.

Проверка Bybit-файлов в `minute_capacity` (`volume = buy + sell`, `trades ≥ 1`)
к BingX не применяется: это правило расчёта ликвидности Bybit, а не формата
тестера. Расчёт ликвидности и базовых лотов по BingX не запускается.

Пример строки (значения колонок):

```text
1791244800000, 405.97, 405.97, 405.92, 405.92, 9.84, 0.0, 0.0, 0
```

## Incremental-докачка

Основной режим работы:

```json
"download_mode": "incremental"
```

Для каждой пары и каждого дня логика следующая:

1. Определить обычный тикер в его точный BingX API symbol.
2. Использовать папку `<bot_root>\tester\data\bingx\<api_symbol>\` для хранения данных этой пары.
3. Если нужного дневного файла нет — скачать его.
4. Если файл уже существует и успешно проходит проверку — пропустить его.
5. Если файл существует, но неполный или повреждён — скачать этот день заново и заменить файл.

Пример для PANW:

```text
<bot_root>\tester\data\bingx\NCSKPANW2USD-USDT\
```

Допустим, в этой папке уже есть валидные файлы до:

```text
2026-10-08
```

Через несколько дней пользователь меняет дату конца (в поле «Конец» панели или в `end_date` блока `bingx` для ручного запуска):

```text
2026-10-11
```

Тогда скрипт не должен перекачивать старые данные. Он должен скачать только отсутствующие дни:

```text
2026-10-09
2026-10-10
2026-10-11
```

с учётом правила «Доступность дневных данных».

Incremental-проверка выполняется отдельно для каждой папки API symbol, поэтому у разных тикеров могут быть разные последние локально доступные даты.

## Проверка существующих дневных файлов

Дневной файл считается валидным только если:

- это parquet формата из раздела «Формат дня (parquet тестера)»: имена, порядок
  и типы колонок, REQUIRED, ZSTD у всех колонок, метаданные ровно
  `hb.schema = candles_1m/1`;
- содержит хотя бы одну и не больше 1440 строк (для дня листинга — не больше
  числа минут от `launchTime` до 23:59 UTC включительно); пропуски минут без
  сделок допустимы;
- каждый `timestamp` — начало минуты (кратен 60 000 мс), относится к дате из
  имени файла и не раньше минуты `launchTime`;
- `timestamp` строго возрастают (значит, не повторяются);
- в OHLCV нет NaN и бесконечностей;
- `buy_volume`, `sell_volume` и `trades` равны `0`;
- `high >= max(open, close, low)`, `low <= min(open, close)`, `volume >= 0`.

Если существующий файл не проходит проверку, день перекачивается. Прежние
`_1m.csv` загрузчик не читает и не создаёт.

## Доступность дневных данных

Данные BingX за календарные сутки становятся доступны для скачивания примерно через 6 часов после окончания суток (00:00 UTC). Частичных дней не бывает: день либо скачивается целиком, либо не скачивается.

Правила:

- текущий UTC-день не скачивается никогда, даже если дата конца указывает сегодняшнюю дату;
- предыдущий UTC-день скачивается, только если с момента окончания этого дня прошло не менее 9 часов (6 часов + 3 часа запаса), то есть текущее время не раньше 09:00 UTC;
- если сейчас раньше 09:00 UTC, последний доступный день — позавчерашний.

Дни после последнего доступного дня пропускаются без ошибки и скачиваются при следующем запуске.

## Безопасная запись файлов

Скачанный день сначала записывается во временный файл в той же папке
(`.PANWUSDT2026-06-13_1m.parquet.<случайное>.tmp`), затем читается обратно и
проходит полную проверку из раздела выше.

Только после успешной проверки он становится финальным
`PANWUSDT2026-06-13_1m.parquet`:

- новый день — `os.link`: существующий файл никогда не перезаписывается; если
  файл дня успел появиться, он проверяется, и невалидный считается ошибкой дня;
- явная перекачка (повреждённый файл или режим `overwrite`) — `os.replace`
  поверх старого файла.

Временный файл удаляется в любом случае. Если загрузка оборвалась, не остаётся
обрезанного `.parquet`, который выглядит как готовый файл.

## Ошибки одной пары не останавливают весь процесс

Ошибка при загрузке одного тикера или одного дня не должна завершать весь скрипт.

Например:

```text
PANW — успешно
BABA — ошибка
TSLL — успешно
```

После ошибки BABA скрипт продолжает обработку TSLL.

В конце должна выводиться итоговая статистика как минимум по следующим категориям:

- скачано новых дней;
- пропущено уже валидных дней;
- перекачано повреждённых дней;
- дней без сделок (файл не создаётся);
- ошибки по дням/парам.

## Windows launcher

Как и остальные командные файлы проекта, лежит в `scripts\`.

`scripts\run_bingx_download.bat` должен:

- запускать `scripts\download_bingx_data.py` через Python из локального окружения проекта `.venv` (как `scripts\calculate_bybit_base_lots.cmd`);
- не зависеть от текущей папки (пути строятся от расположения самого `.bat`);
- после завершения оставлять окно консоли открытым, чтобы пользователь видел результат или ошибку.

Запуск должен быть возможен двойным кликом по:

```text
scripts\run_bingx_download.bat
```

Основной сценарий запуска — кнопка «Подготовить файлы» в панели (этап 2); `.bat` нужен для ручной докачки.

## Зависимости

Зависимостей должно быть как можно меньше.

Где возможно, использовать стандартную библиотеку Python.

## Что не входит в этап 1

Сейчас не добавляем:

- другие биржи кроме BingX;
- панель, UI и кнопки — это этап 2;
- базу данных;
- scheduler;
- автоматический запуск Hamster-тестов после загрузки.

На первом этапе задача только одна: получить надёжный загрузчик и докачку исторических 1m данных BingX с ручным запуском.

При этом ядро загрузки должно быть написано так, чтобы панель могла передавать ему пары и даты напрямую, без переписывания механизма загрузки, проверки и сохранения данных.

# Этап 2 — режим BingX в панели (СКРИНЕР 01 и RUNNER 01)

## Цель

Встроить загрузчик из этапа 1 в панель. На карточках СКРИНЕР 01 и RUNNER 01 появляются две галочки:

- **Режим BingX** — тестер работает на BingX (символы, комиссии, стратегия, данные из `tester\data\bingx\`);
- **Докачать данные BingX** — перед подготовкой докачать недостающие дни; галочка неактивна (и снята), пока «Режим BingX» выключен.

| Режим BingX | Докачать | «Подготовить файлы» |
| --- | --- | --- |
| выкл | недоступна | как сейчас (Bybit), без изменений |
| вкл | вкл | докачка недостающих дней, затем подготовка файлов |
| вкл | выкл | подготовка на уже скачанных данных |

## Что не входит в этап 2

- удалённый тестер (`remote_runner`) — режим BingX только для локального тестера;
- крипто-пары — только стоки TradFi;
- изменения логики Bybit-режима.

## Тестер и папка данных

С 2026-10-16 `tester_runner.bot_root` указывает на новый тестер, который читает parquet; прежняя установка тестера переименована и хранит исходные CSV.

Папка данных BingX вычисляется из `bot_root`, отдельный путь не нужен:

```text
<bot_root>\tester\data\bingx\<API symbol>\<тикер>USDT<YYYY-MM-DD>_1m.parquet
```

Пример:

```text
<bot_root>\tester\data\bingx\NCSKPANW2USD-USDT\PANWUSDT2026-06-13_1m.parquet
```

Имя папки `bingx` — это `exchange.name` (`BingX`) в нижнем регистре, так же как Bybit-данные лежат в `tester\data\bybit\`.

## Настройки в общем конфиге

Панель использует тот же блок `bingx` в `config.local.json`, что и ручной запуск (этап 1), — из него берётся `download_mode`. `start_date`, `end_date` и `pairs` из блока панелью не используются: пары и даты берутся из полей экрана, на котором нажата кнопка.

Ключи, если нужны, берутся из `<bot_root>\settings_accounts\bingx.json` (см. этап 1). Для запуска стратегий используется тот же аккаунт Hamster `bingx`.

## Поведение в режиме BingX

При нажатии кнопки «Подготовить файлы» на экране SCREENER 01 «Скринер пар» или RUNNER 01 «Локальный runner» с включённым «Режим BingX»:

1. **Тикеры.** Пары берутся из поля ввода экрана, на котором нажата кнопка: «Пары для скрининга» (SCREENER 01) или «Пара инструментов» (RUNNER 01). Пользователь вводит привычные тикеры (`PANW` или `PANWUSDT`); суффикс `USDT` отбрасывается, тикер сопоставляется с API symbol по правилу этапа 1 (`PANW` → `NCSKPANW2USD-USDT`).
2. **Докачка данных** (только если включена «Докачать данные BingX»). Для каждой пары вызывается загрузчик этапа 1 в режиме из блока `bingx` за диапазон `StartDate − 1 день` … `EndDate`, где даты берутся из полей «Начало» и «Конец» того же экрана, с учётом правила «Доступность дневных данных». Лишний день в начале нужен для прогрева тестера (`WarmupDays: 1` в шаблонах конфига тестера). Уже валидные дни не перекачиваются; если дата конца сдвинута вперёд, докачиваются только новые дни, и их parquet-файлы кладутся в папку пары.
3. **Проверка локальных данных** (всегда, с докачкой и без). Все дни `StartDate − 1 день` … `EndDate` (кроме дней до листинга и ещё недоступных дней) должны лежать в папке пары и проходить проверку дневного файла; день без файла допустим, только если BingX подтверждает, что сделок в этот день не было (один запрос на такой день). Других запросов свечей проверка не делает и файлов не пишет. Если каких-то дней нет, подготовка не выполняется, а панель показывает пары и дни и предлагает включить «Докачать данные BingX».
4. **Конфиг тестера.** Шаблон заполняется так же, как сейчас, со следующими отличиями:
   - в `settings[*].basic.symbol` — API symbol (`NCSKPANW2USD-USDT`);
   - `StartDate` / `EndDate` — даты из панели;
   - `MakerFee: 0.00012` (0.012%), `TakerFee: 0.0003` (0.03%) — базовые 0.02%/0.05% со скидкой 40%, как в `templates/exchanges/BingX/mrs3-tester.json` (решение пользователя 2026-10-16);
   - `UpdateData: false` — коннектор тестера к BingX данные не скачивает, данные берутся только из папки.
5. **Стратегия.** В файле стратегии `settings_strategy`:
   - `exchange.name: "BingX"`;
   - `exchange.account: "bingx"`;
   - `basic.symbol` — API symbol.
6. Дальше «Старт» / «Стоп» работают как сейчас.

Если тикер не найден на BingX, данные по паре не докачались или каких-то дней нет локально, подготовка не выполняется, а панель показывает, по какой паре ошибка. Частичный запуск без данных не допускается. Если два введённых тикера указывают на один контракт (`AMD`, `AMDSTOCK`), символ попадает в тестер один раз.

Докачка может занимать время, поэтому выполняется в фоновом потоке панели (одна докачка одновременно) с отображением прогресса: `POST /api/v2/testing/bingx/download` запускает докачку, `GET /api/v2/testing/bingx/status` отдаёт состояние (`running` / `done` / `failed`), число обработанных дней, итоговую статистику, ошибки и найденные API symbols. Если докачка завершилась с ошибками, подготовка файлов не запускается. Пока докачка идёт, подготовка в режиме BingX отклоняется.

## Изменения в коде

- Панель вызывает ядро `src/mrs3/bingx_downloader.py` напрямую, передавая пары и даты из полей экрана и `download_mode` из блока `bingx`.
- Проверка символа в панели (`_SYMBOL = ^[A-Z0-9]{2,32}$` в `src/mrs3/panel_testing.py`) в режиме BingX должна пропускать API symbol с дефисом (`NCSKPANW2USD-USDT`).
- Подстановка `exchange`, комиссий и `UpdateData` выполняется только при включённом «Режим BingX»; Bybit-шаблоны не меняются.
- Скринер при оценке результатов в режиме BingX берёт дату листинга из `launchTime` BingX, а не из Bybit. Режим определяется по символам в отчётах: BingX API symbol содержит `-`, Bybit-символ — нет; смесь BingX и Bybit символов в одной папке отчётов — ошибка.
- Скринер в режиме BingX не записывает вердикты в реестр ликвидности Bybit (`input/bybit_tradfi_liquidity.xlsx`, лист «Скрининг»): результаты только показываются в панели и в экспорте. Автоматическая запись вердиктов BingX в Excel отложена.

## Лист «Скрининг BingX»

В реестре `input/bybit_tradfi_liquidity.xlsx` рядом с листом «Скрининг» создаётся лист «Скрининг BingX» той же формы: та же шапка, ширины колонок, оформление, автофильтр, закрепление, выпадающие списки и условное форматирование.

- В лист попадают только пары листа «Скрининг», которые есть на BingX (сопоставление по правилу этапа 1); пары, которых на BingX нет, не записываются.
- «Пара» — человеческий тикер BingX: базовый тикер + `USDT` (`PANWUSDT`; `AMDSTOCKUSDT` → `AMDUSDT`).
- «Листинг» — дата листинга BingX (UTC-дата `launchTime`).
- Остальные колонки остаются пустыми: результаты Bybit не копируются, их заполняет оператор.
- Лист создаёт и пополняет `scripts/build_bingx_screening_sheet.py`. Повторный запуск только дописывает новые пары и не трогает уже заполненные строки; если добавлять нечего, файл не перезаписывается. Перед записью рядом создаётся резервная копия `bybit_tradfi_liquidity.backup-<время>.xlsx`.

## Предусловие

BingX-структура данных и пробная BingX-стратегия сейчас есть только в другой, более новой установке тестера, где `hb_c.exe` от 2026-10-09, а в `<bot_root>` — от 2026-09-14. Нужно было одним пробным прогоном подтвердить, что тестер в `<bot_root>` запускается на данных из `tester\data\bingx\`. Выполнено 2026-10-11: прогон скринера по TSLL (304 прогона) шёл на `NCSKTSLL2USD-USDT` с данными BingX и принят пользователем.

## Критерии готовности

- «Режим BingX» выключен — Bybit-запуски скринера и RUNNER 01 работают как раньше, «Докачать данные BingX» недоступна.
- «Режим BingX» и «Докачать» включены — для пар из панели в `<bot_root>\tester\data\bingx\` появляются папки с parquet-файлами дней за `StartDate − 1` … `EndDate`, конфиг тестера и стратегия заполнены по правилам выше, тестер запускается и выдаёт отчёты.
- Повторная подготовка с датой конца, сдвинутой вперёд, докачивает только новые дни.
- «Режим BingX» без докачки готовит файлы на уже скачанных данных и отказывает с перечнем дней, если данных не хватает.
- Parquet (2026-10-16): загрузчик пишет и проверяет только `_1m.parquet` формата тестера; файл, записанный загрузчиком из CSV-строк BingX, совпадает по схеме, метаданным, сжатию и значениям с результатом встроенного конвертера тестера на том же CSV (сверка на сконвертированном архиве); короткий прогон тестера на parquet-данных BingX даёт сделки и совпадает с прогоном той же стратегии на прежних CSV.
