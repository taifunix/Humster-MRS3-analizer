# Source v6 BASE 1ORD selection — specification

**Status:** Implemented and verified
**Date:** 2026-08-24
**Depends on:**
[canonical phase 1](2026-08-16-mrs3-v07-canonical-phase1.md), §15 и §17;
[analysis shortlist / READY JSON](2026-08-18-analysis-shortlist-ready-json-contract.md);
[metric contract](2026-08-23-source-v6-metric-contract.md), M2;
[ADR-0009](../decisions/0009-canonical-phase1-surface-selection-contract.md)

## Зачем

Одноордерные стратегии из панели практически недоступны, и это три разные
неисправности, наложившиеся друг на друга.

**Первая: выбирается один кандидат вместо нескольких.** Замер на реальной
`CXMT_2026-07-29_2026-08-17.analysis-v6.duckdb`: доступно **49** плато с
замороженным BASE, выбирается **8** — по одному на TF.

**Вторая: отбор смещён в пользу слабых плато.** Корреляция размера плато с
`pnl_dd5_theoretical` — **−0.22**, отрицательная. Ранжирование по одному PnL
систематически предпочитает мелкие плато. Размеры выбранных сейчас ТОП-1:
`[2, 2, 3, 4, 5, 5, 8, 27]` при медиане пула 6. Три из восьми — плато из 2–3
точек, то есть минимально возможные: это две-три соседние ячейки сетки, которые
случайно сработали, а не зона устойчивости.

**Третья: выбранный кандидат недостижим.** Пять TF из восьми (1h, 2h, 3h, 30m,
45m) имеют BASE и ноль многоордерных структур. `base_one_order` хранит *точки*,
а `generate_fresh_analysis_strategies` читает только `structures`, — эти пять TF
не дают ни одной стратегии вообще, хотя §17 требует обратного.

## Что говорит контракт

§17, дословно:

> For each exact scope, one frozen local BASE per Plateau becomes a BASE
> candidate. **Rank at most three** by:
> `PnL@DD5 theoretical DESC, raw PnL DESC, Trades DESC, DD ASC, PointID ASC`
>
> Do not add Shift or EventCount to this Top-3 ranking.

и там же:

> Panel/controller must derive selectable scopes from the canonical published
> run/surface plus persisted Plateau BASE facts, not only from 2–4ORD candidates.
> **A scope with BASE 1ORD but no multiorder candidate must remain selectable.**

§15 задаёт пул: по одному замороженному BASE на каждое READY-плато, из
continuity-usable представителей, чья исходная точка `standalone_eligible == True`.

**Этот документ сознательно изменяет §17 в двух местах** — число кандидатов и
способ их отбора. Оба изменения перечислены явно в B3 и B4.

## Где сломано

[`src/mrs3/selection.py:643-652`](../../src/mrs3/selection.py#L643):

```python
for _, group in local.groupby(["symbol", "side"], sort=True):
    selected_rows.append(group.sort_values(...).iloc[0])
```

- `.iloc[0]` — один вместо нескольких;
- `groupby(["symbol", "side"])` — без `timeframe`, тогда как контракт требует
  «exact scope» = `Pair + Side + TF`.

Второе замаскировано: fresh-анализ вызывает `_analyze_points` отдельно на каждый
scope. Но legacy-путь [`pipeline.py:448`](../../src/mrs3/pipeline.py#L448) подаёт
несколько TF одним кадром — и там из всех TF остаётся один BASE.

Минимума по размеру плато нет вовсе: плато готово, если хотя бы **одна** его
точка прошла экономику ([`plateau.py:263`](../../src/mrs3/plateau.py#L263)).

## Контракт

### B1 — Пул кандидатов не меняется

Пул — замороженные `base_1ord_point_id` READY-плато (§15). Реселекции нет:
`select_base_one_order` только воспроизводит замороженные факты и падает
закрыто, если точка отсутствует или дублируется.

### B2 — Отбор идёт по точному scope

Группировка — `["symbol", "side", "timeframe"]`. Докстринг привести к «per exact
scope». Исправляет legacy-путь, не меняет поведение fresh-пути.

### B3 — Допуск кандидата: два фильтра до ранжирования

Кандидат участвует в отборе, только если его плато удовлетворяет обоим:

| Фильтр | Значение по умолчанию | Смысл |
| --- | --- | --- |
| размер плато ≥ `min_plateau_points` | **3** | плато из двух ячеек — не зона устойчивости |
| событий за месяц ≥ `min_plateau_events_per_month` | **20** | плато должно торговать, а не случайно совпасть |

Оба порога — в конфиге (B8), потому что подбираются эмпирически на других парах.

**Замеренное поведение на текущем корпусе.** Фильтр размера отсекает 8 из 49
кандидатов, все размера 2, и срабатывает ровно там, где нужно: на 5m вместо
плато из 2 точек набор становится `[15, 23, 12, 7]`, на 4h вместо двойки —
`[6, 4, 3]`.

Фильтр событий на этом корпусе **не отсекает ничего**: минимум по 49 плато — 22
события за 20 дней, порог 20 ниже фактического минимума. Это зафиксировано
сознательно как страховка для других пар; на текущих данных его действие
непроверяемо, и его тест обязан быть синтетическим.

### B4 — Четыре слота по ролям вместо ранжирования одним списком

§17 ранжирует единым списком, из-за чего все места могут занять мелкие плато.
Вместо этого — четыре слота, и **формула §17 остаётся формулой ранжирования во
всех слотах**; меняется только множество, по которому слот ранжирует:

| Слот | Роль | Множество |
| --- | --- | --- |
| 1 | `ECONOMY_1` | весь допущенный пул |
| 2 | `STABILITY_1` | оставшиеся плато с размером ≥ замороженной медианы |
| 3 | `STABILITY_2` | то же |
| 4 | `ECONOMY_2` | оставшийся допущенный пул |

Медиана считается ровно один раз из полного допущенного пула этого scope до
первого выбора и потому не является настраиваемым числом.

**Дедупликация обязательна.** Кандидат, попавший в слот, не занимает следующий.
После четырёх ролей незаполненная ёмкость до `base_one_order_slots` добирается
из оставшегося допущенного пула по той же формуле §17, с ролями `FALLBACK_n`.
Если допустимых уникальных плато меньше лимита, scope честно возвращает меньше
кандидатов.

Число слотов — в конфиге (B8).

### B5 — Нормировка событий на месяц

`min_plateau_events_per_month` сравнивается с числом событий плато **за
последний месяц** периода:

- период короче 30 дней → берутся все события, без экстраполяции вверх;
- период длиннее 30 дней → берутся только события последних 30 дней.

Это исключает преимущество плато с более длинным исследованным периодом.

**Требуется новое поле.** Метки времени событий существуют только в момент
материализации: `trip.timestamp_ms` живёт в воркере, используется для проверки
попадания в witness ([`source_v6_materializer.py:80`](../../src/mrs3/source_v6_materializer.py#L80))
и **не сохраняется**. В surface и analysis DB уходят только `event_ids` и
`point_event_count`, по которым время события восстановить нельзя.

Поэтому воркер дополнительно считает и кладёт в `row_json` поле
`events_last_30d` — число событий точки, попавших в последние 30 дней окна.
Метки времени у него уже в руках, второе число почти бесплатно.

Отвергнутые варианты: сохранять timestamp каждого события — заметно раздувает
`row_json`; считать при анализе — потребует декодировать payload'ы и отменит
работу по W9.

`plateau_event_count` за последний месяц — объединение `events_last_30d` точек
плато тем же способом, что и полный счёт.

**Оговорка о точности.** `plateau_event_count` — сумма событий точек плато без
фактической дедупликации: id события включает `point_key`
([`source_v6_stitch.py:703`](../../src/mrs3/source_v6_stitch.py#L703)), поэтому
две точки одного плато не могут разделить событие даже поймав один и тот же
рыночный импульс. Проверено: на всех 64 готовых плато объединение точно равно
простой сумме. Как **порог допуска** это приемлемо (вопрос «торговало ли плато
вообще»), как **вес силы плато** — нет, и в ранжирование оно не входит.

### B6 — BASE-кандидат должен быть выбираем

`base_one_order` остаётся как есть — это точки, доказательства отбора.
Дополнительно fresh-анализ **сохраняет BASE как структуру-кандидата** в таблицу
`structures`, построенную существующим `_base_structure`
([`pipeline.py:241`](../../src/mrs3/pipeline.py#L241)): `order_count = 1`,
`structure_id = "BASE_<digest>"`, `status = READY_MRS3_STRUCTURE`.

DDL не меняется — `structures` это `(scope_key, payload_json)`. Генератор уже
готов: есть ветка `methods = (LotMethod.EQUAL,) if order_count == 1`. Признак
происхождения уже есть — префикс `BASE_`.

После этого `list_fresh_analysis_shortlist` считает `1ORD` из `structures`
(`order_count == 1`), а не из `base_one_order`, и BASE попадает в
`candidate_ids`. Временное решение от 2026-08-23 этим отменяется.

### B7 — Один ордер даёт только EQUAL

Без изменений, §17: `1ORD -> EQUAL only`. Четыре BASE на scope дают четыре JSON,
не восемь.

### B8 — Пороги живут в конфиге

Новая секция `config.local.json`, рядом с существующей `plateau`:

```json
"base_one_order": {
  "min_plateau_points": 3,
  "min_plateau_events_per_month": 20,
  "slots": 4
}
```

Все три поля входят в `AlgorithmConfig` и, следовательно, в
`algorithm_config_sha256` и в `analysis_id`. Это **желаемое** поведение: другой
порог даёт другой набор стратегий, и он обязан быть другим артефактом с другой
идентичностью, иначе два разных результата лежали бы под одним `analysis_id`.

Цена подбора низкая: пересчёт анализа читает готовые строки из surface, не
декодирует ни одного payload и не трогает Source DB. Меняется только анализ, не
материализация.

**Не выносится в конфиг:** ранжирование §17 — это определение «лучшего», а не
эмпирический порог; правило медианы в слотах 2–3 — самокалибрующееся.

### B9 — Две цифры плато доходят до пост-тестового сравнения

Историческое post-test сравнение объединяло результаты тестера с таблицей вариантов генерации,
и список переносимых колонок — белый
Поэтому числа передаются
через таблицу вариантов и добавляются в этот список:

| Поле | Смысл |
| --- | --- |
| `plateau_point_count` | сколько точек сетки образуют плато |
| `base_point_trades` | трейды выбранной BASE-точки — то, что реально торгует стратегия |
| `plateau_total_trades` | сумма трейдов по всем точкам плато — активность зоны целиком |

Оба числа трейдов приносятся сознательно: они отвечают на разные вопросы, и
второе завышено кратно числу точек, что при сравнении надо видеть явно.

Для многоордерных структур поля заполняются по плато каждого ордера; правило их
агрегации — вне объёма этого документа и здесь не вводится.

## Инварианты

- Кандидаты берутся только из замороженного пула; реселекции и добавления нет.
- Порядок ранжирования §17 не меняется ни в одном слоте.
- Кандидат не занимает более одного слота.
- Кандидат, лучший по экономике, присутствует всегда.
- Число кандидатов на scope не превышает `slots` и не превышает размер пула.
- `len(BASE_1ORD variants) == len(base_one_order)` — существующая проверка
  [`pipeline.py:356`](../../src/mrs3/pipeline.py#L356) должна сходиться при
  нескольких кандидатах.
- Имена стратегий остаются уникальными.
- Scope с BASE и без многоордерных структур выбираем и даёт JSON.

## Acceptance evidence

1. Кадр из пяти плато одного `Pair+Side+TF` → четыре кандидата с ролями
   `эконом, устойч, устойч, эконом2`; при равных `pnl_dd5_theoretical` решает
   `pnl_pct`, затем `trades`, затем `dd_pct` ASC, затем `point_id`.
2. Пул из двух допущенных плато → два кандидата, без повторов.
3. Кандидат, одновременно лучший по экономике и устойчивый, занимает слот 1 и не
   дублируется в слоте 2.
4. Кадр с двумя TF одного `Pair+Side` → отбор независим по каждому TF (B2; на
   текущем коде тест падает).
5. Плато из 2 точек не допускается; из 3 — допускается.
6. Плато с числом событий за месяц ниже порога не допускается (синтетический
   тест: на реальном корпусе порог не срабатывает).
7. Период длиннее 30 дней → в счёт идут только последние 30 дней; период короче
   → все события без экстраполяции.
8. На реальном наборе `CXMT_2026-07-29_2026-08-17` результат совпадает с
   замером: **26 кандидатов** вместо 8, распределение по TF —
   `15m [8,12,12,4]`, `5m [15,23,12,7]`, `1h [3,10,13,8]`, `30m [5,31,7,3]`,
   `45m [5,16,20,14]`, `4h [6,4,3]`, `2h [27,3]`, `3h [4]`.
9. Shortlist показывает `1ORD` от 1 до 4 и включает BASE в `candidate_ids`.
10. Scope с BASE и нулём структур выбираем, и `Generate READY JSON` выдаёт JSON.
11. Изменение любого порога в конфиге меняет `analysis_id`.
12. `plateau_point_count`, `base_point_trades` и `plateau_total_trades` доходят
    до таблицы сравнения после теста.

## Non-goals

## Verified evidence (2026-08-24)

`0.7-canonical-phase1-base-1ord-v3` freezes the median once per admitted exact
scope, attempts `ECONOMY_1`, `STABILITY_1`, `STABILITY_2`, `ECONOMY_2`, then
fills unused capacity from the remaining admitted pool as `FALLBACK_n`.
Stability roles alone require `plateau_point_count >= frozen_median`.

Fresh CXMT evidence with 30 materialization, 30 publication and 8 analysis
workers produced the acceptance vectors and 26 BASE candidates; 5m added only
the size-7 `FALLBACK_1` candidate. Full suite: 1736 passed, 2 skipped.

- Изменение пула, критериев заморозки BASE или §15.
- Изменение порядка ранжирования §17.
- Использование числа событий как веса силы плато (см. оговорку в B5).
- Дедупликация событий по времени: порог «насколько близко считать одним
  событием» так же произволен, как и то, от чего мы уходим.
- Перенос BASE в отдельную таблицу или изменение DDL.
- Правило агрегации полей B9 для многоордерных структур.
