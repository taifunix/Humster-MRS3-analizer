  - работа по Panel, PerformanceDB, оптимизатору.

**Шаги:**

2. **Страховка до любых операций:** `git branch backup/bingx-before-merge-2026-10-16` на текущем HEAD и `git push origin backup/bingx-before-merge-2026-10-16`.

4. **Слияние:** `git merge origin/main` (не rebase, не `reset`, не `checkout --` поверх локальных правок). Если слияние пошло не так — `git merge --abort` и обратиться к пользователю. Конфликты разрешать вручную, сохраняя обе стороны по смыслу. Ожидаемые места пересечения:

## Часть B. Упаковка свечей BingX в parquet формата тестера

**Зачем.** Новый тестер читает минутные свечи только из parquet; механизм BingX сейчас пишет CSV.

**Формат дня (как пишет сам тестер, сверено с эталоном):**
- путь — `<папка данных биржи>/<SYMBOL>/<SYMBOL><YYYY-MM-DD>_1m.parquet` (имя папки биржи и расположение — как ожидает тестер для BingX; проверить по конфигу и документации тестера и по тому, где сейчас лежат CSV BingX);
- колонки ровно в этом порядке: `timestamp` INT64 (начало минуты, мс UTC), `open`, `high`, `low`, `close`, `volume`, `buy_volume`, `sell_volume` DOUBLE, `trades` INT32;
- все колонки **REQUIRED** (не nullable);
- сжатие **ZSTD**;
- в key-value метаданных файла ровно одна запись `hb.schema = candles_1m/1`, без `ARROW:schema`;
- строки — только минуты со сделками, по возрастанию, без дублей, внутри своих суток UTC;
- проверки: `timestamp` кратен минуте; цены > 0; `volume == buy_volume + sell_volume` точно (в десятичной записи), `high ≥ max(open, low, close)`, `low ≤ min(...)`, `trades ≥ 1`.

**Готовая эталонная реализация** — в `main` после части A, `src/mrs3/portfolio/minute_capacity.py`:
- `PARQUET_SCHEMA` и `PARQUET_KEY_VALUE` — схема;
- `_to_parquet(csv_bytes)` — CSV формата `timestamp,open,high,low,close,volume,buy_volume,sell_volume,trades` → байты parquet (pyarrow, `ParquetWriter(..., compression="zstd", store_schema=False)` + `add_key_value_metadata`). DuckDB не годится: он не умеет ставить REQUIRED;
- `_read_day_bytes` — проверка содержимого (имена и типы колонок, инварианты строк). REQUIRED, ZSTD и метаданные он не проверяет — их проверяет шаг B2 отдельно.

Переиспользуй их (или вынеси в общий модуль), не пиши вторую версию формата.

**Особенности BingX — выяснить и записать в спецификацию:**
1. Какие поля даёт источник BingX. Если нет разбивки объёма на buy/sell или числа сделок, сохранить ту семантику, которую сейчас использует CSV-упаковщик BingX (не придумывать новую), и обеспечить инварианты выше: например, `buy+sell == volume` точно; `trades ≥ 1` только для минут с объёмом; минуты без объёма не писать — как у тестера Bybit. Решение согласовать с пользователем.
2. Неполный текущий день не писать: только полные сутки UTC.

**Шаги:**
1. Спецификация (новая или дополнение спецификации загрузчика BingX): формат, источник полей, атомарная запись (временный файл → проверка чтением → `os.link`, существующий день не перезаписывать), миграция CSV → parquet.
2. TDD. Проверки:
   - схема и метаданные совпадают с эталоном `reference_bybit_tester_day_…parquet` (`pq.ParquetFile(...).schema_arrow`, `.metadata.metadata`, сжатие колонок);
   - валидатор `_read_day_bytes` принимает файл.
3. Перевести загрузчик BingX на запись parquet. Существующие CSV-дни BingX сконвертировать в parquet атомарно; CSV не удалять до подтверждения пользователя.
4. **Проверка тестером:** один короткий прогон (одна стратегия, несколько дней) на паре BingX по новым parquet. Тестер должен прочитать данные без ошибок, сделки — появиться. Если есть возможность, сравнить с прогоном той же стратегии на прежних CSV: результат должен совпасть.

**Отчёт части B:**
- поля BingX и их семантика;
- сколько дней сконвертировано;
- сверка схемы с эталоном;
- результат прогона тестера;
- коммит.

## Часть C. Генератор периодных CSV из Source v6 (история → рабочая база анализа)

**Цель.** Не перегонять историю всех пар в тестере, а построить из полных баз Source v6 MRS2 периодные CSV **в точном формате CSV тестера** (`reports_history.csv` + `run_snapshot_*.json`). Они будут загружены в рабочую базу анализа через CSV Direct, затем пополняться новыми прогонами тестера, и по ним будут строиться READY для реальной торговли. Схема периодов, оценки и READY — в `docs/superpowers/plans/2026-10-15-plateau-v4-validation-plan.md`, разделы **P2**, **A12a**, «Итоговые правила READY v4». Прочитать их.

**Что генерировать:**
- биржа Bybit, сторона LONG, все пары, где есть Source v6 MRS2;
- сетка — подмножество, которое есть в Source v6:
  - шифты 70, 90, 110, 140, 170, 200, 230, 270, 310, 350, 390, 430, 470, 510, 550 bp (множитель LONG = 1 − bp/10000, ровно);
  - TF 15m, 30m, 45m, 1h, 2h, 3h, 4h (5m — отдельным флагом, по умолчанию выключен). Source v6 содержит все 8 TF (5m…4h); если у какой-то пары TF нет, этот TF для пары пропускается и записывается в журнал;
  - Open/Close MA 2–7, SMA ohlc4.
- **периоды** (раздел P2):
  - от даты листинга + 4 дня до конца последних полных суток UTC, которые покрывает Source v6 (EndDate = начало следующих суток);
  - максимальное число полных 20-дневных периодов, остаток добавляется к последнему (20–39 дней);
  - в CSV `StartDate`/`EndDate` — границы периода;
  - режим «с указанной даты» для пар с длинной историей — параметром.
- один CSV = одна пара × один период: строка на точку (TF × шифт × Open × Close), все колонки как в эталоне `grid750_*/reports_history.csv` (в том числе `MonthlyReturn_YYYY_MM` для месяцев периода и колонки `settings[*]…`), `PairsCount` = 1;
- рядом — `run_snapshot_<имя>.json` в формате эталона: настройки с `basic.use_fix = true`, `exchange.use_upnl = false`, тип и источник MA (SMA, ohlc4) для LONG; `my_fix_balance` / `InitialBalance` = 10000;
- журнал периодов (JSONL или CSV): пара, сторона, период, источник `source_v6_generated`, база Source v6 и её хеш/ревизия, хеш CSV, число строк, статус.

**Семантика должна повторять тестер** (иначе на стыке с будущими прогонами тестера поедут пороги):
1. **Старт периода без позиции.** Тестер начинает каждый период пустым, прогрев MA 4 дня назад без сделок. В Source v6 прогон непрерывный, поэтому сделки, открытые до начала периода, не учитываются.
2. **Конец периода.** Выяснить по эталону, как тестер считает открытую на конце позицию: входит ли нереализованный результат в `TotalPnL` / `FinalBalance` / `MaxDrawdown`, считается ли сделка в `TotalTrades`. Повторить.
3. **Метрики** (определить по эталону и коду отчёта тестера, если доступен):
   - `TotalPnL`, `TotalPnLPercent` = TotalPnL / InitialBalance × 100;
   - `MaxDrawdown(Percent)`;
   - `UlcerIndex` — тестер считает по **часовой** эквити;
   - `TotalTrades` (вход → полный выход), `Win` / `Los` / `WinRate`, `Fills`, `TotalFees`, `ProfitFactor` (`n/a` без убыточных), `PositionAvgPercent` / `PositionMaxPercent`, `MonthlyReturn_*`.

   Нужны дневные или часовые ряды эквити из фрагментов Source v6 (замеры баланса/эквити разрежены). При необходимости восстановить часовую эквити из цепочки сделок и часовых свечей.
4. **Размер лота.** Source v6 MRS2 считан на лоте 100 USDT (большинство скоупов) и 1000 USDT (часть), а тестер — 10 000. Проценты в основном сопоставимы, но у дорогих бумаг округление шага количества различается. Пересчитать в процентах; пары, где сверка (ниже) показывает систематическое расхождение, пометить в журнале.

**Требования загрузчика CSV Direct** (`load_csv_direct` в ветке `feat/csv-direct-analysis`, отправлена в origin 2026-10-16 как прототип, в main не слита; список ниже — контракт, дополнительно проверить сгенерированные CSV загрузкой из этой ветки, не сливая её в main). CSV должен им удовлетворять:
- обязательные колонки как в эталоне; без дублей заголовков и лишних полей в строках;
- `PairsCount` = 1;
- ровно один активный множитель LONG на строку; шифт точно целый в bp; длины MA — положительные целые;
- без повторяющихся точек;
- `use_fix` / `use_upnl` из snapshot (фиксированный лот);
- snapshot лежит в папке CSV или выше; в `settings[].basic.symbol` — пара, в `mrs2.ma_long` / `ma_close_long` — тип и источник MA;
- `TotalPnL / InitialBalance × 100` совпадает с `TotalPnLPercent`;
- `Win + Los ≤ TotalTrades ≤ Fills`; `WinRate` в 0…100 и согласован со сделками; `MaxDrawdownPercent` ≥ 0; `ProfitFactor` ≥ 0 или `n/a`;
- `EndDate` > `StartDate`; одна пара дат на один вызов загрузки (значит, каждый период загружается отдельно);
- для каждой пары нужна дата листинга (из реестра проекта / `dates.xlsx`) — включить её в журнал;
- сетка полная — прямоугольная по шифт × Open × Close в каждом TF.
