Preflight на валидной v2-базе отрабатывает и возвращает 56 scope с реальными статусами. Каталог Source DB показывает ровно существующий файл. Bootstrap подставляет настоящие пути в поля с атрибутом name (экран «Тестирование»). Навигация, роутинг по hash, aria-разметка и live-region сделаны аккуратно. v1-артефакты корректно не попадают в каталог.

1. Экран «Настройки» показывает выдумку, а «Сохранить» её записывает
Самое серьёзное.

loadSafeDefaults() подставляет значения по атрибуту name. У всех полей на экране настроек name отсутствует — они навсегда остаются с зашитыми в HTML значениями:

Поле в панели	Показывает	Реально в config
Source DB root	configured source DB root	configured `local_source_db_root`
Output root	configured output root	configured `local_output_root`
Listing dates	configured listing dates file	configured `listing_dates_path`
То есть экран настроек выглядит так, будто показывает вашу конфигурацию, а показывает фикцию. Это хуже, чем не показывать ничего.

И settingsPayload() собирает все поля сразу, независимо от того, какую карточку вы сохраняете. Нажатие «Сохранить runner paths» отправит заодно local_source_db_root, local_output_root, listing_dates_path, algorithm_version и import_workers — то есть перезапишет пять посторонних реальных настроек выдуманными. Это путь к потере конфигурации в одно нажатие.

2. Кнопки говорят «ожидает backend» и при этом выполняют действие
21 кнопка из 48 несёт data-pending и печатает «… ожидает backend». Но часть из них одновременно имеет реальные обработчики — оба слушателя срабатывают.

sourceOperation привязывается позиционно: const [preflight, , start] = buttons. В карточке локального импорта три одинаковых на вид кнопки ведут себя по-разному:

Кнопка	Сообщение	Что делает на самом деле
Проверить вход и target	«ожидает backend»	реально делает preflight
Сохранить путь	«ожидает backend»	ничего
Старт импорта	«Старт локального импорта ожидает backend»	реально запускает импорт
Панель сообщает «не реализовано» в момент, когда пишет базу. По экранам: Source DB — 9 из 9 кнопок с этой надписью, Настройки — 8 из 8, при том что обе группы частично рабочие.

Позиционная привязка ещё и хрупкая: добавление кнопки в ряд молча меняет поведение соседних.

3. Вся диагностика стирается на границе

def surface_preflight(self, payload):
    try:
        return self._surfaces().preflight(...)
    except Exception:
        raise ValueError("invalid surface request") from None
Проверил три принципиально разные ошибки:

Ситуация	Что видит пользователь
файла нет	{"error": "invalid settings"}
выбрана surface вместо Source DB	{"error": "invalid settings"}
выбран config.local.json	{"error": "invalid settings"}
Это ровно тот класс проблемы, который мы весь день чинили в данных. На уровне данных теперь есть точные диагнозы — OPEN_TAIL_FILTER_REMOVED_ALL_DATA с числом сэмплов, событий и циклов; M7 metric mismatch с объявленным и выведенным значением; карантин с именем и SHA отчёта. Панель выбрасывает всё это и заменяет на «invalid settings». Требование из плана «показывать не „0 candidates“, а причину» на границе API не выполнено.

4. «Check gaps» показывает ноль вместо причины
Бэкенд отвечает содержательно:


{"status": "n/r - Check gaps", "reason": "no common READY interval", "gaps": [], "missing_witnesses": []}
А видимая кнопка выводит: «Gaps 15m: 0.» — то есть «проблем нет» у scope, который заблокирован. reason получен и отброшен.

Причина — два дублирующих рендера scope-списка в одном файле, оба пишут в один и тот же .scope-list: renderSurfaceScopes (строка 589) с плохой диагностикой и renderSurfaceScopesV2 (строка 741), который через showGapReportV2 показывает Reason: и список отсутствующих ячеек. Какой из них увидит пользователь, зависит от того, какой путь отработал последним. Плюс в строке дважды подряд печатается один и тот же текст: 15m · n/r - Check gaps и следом кнопка n/r - Check gaps.

5. Основной маршрут упирается в тупик
На вашей реальной базе: 56 scope, 0 READY, у всех «n/r». Панель здесь не врёт — база действительно не READY. Но дальше идти некуда: нет ни сводки «сколько READY из скольких», ни подсказки, чего не хватает, а единственный диагностический элемент отвечает «0». Пользователь остаётся с 56 одинаковыми строками и без следующего шага.

6. Мелкое, но подрывающее доверие
9 бейджей READY/SAFE зашиты в HTML. Карточка runner показывает зелёный READY рядом с текстом «Проверка runner ещё не выполнена». Бейдж — самый заметный элемент карточки, и он утверждает обратное тексту под ним.
В сайдбаре постоянно висит «backend connection pending», хотя backend отвечает.
Кнопка «Заполнить config_tester.json» стоит выше заголовка карточки — до того, как пользователь понял, о каком runner речь.
Экран «Стратегии и DD5» заявляет полный маршрут до Performance DB и DD5, но shortlist и READY JSON — декоративные кнопки.
Что чинить в первую очередь
Убрать data-pending со всех кнопок, у которых есть реальный обработчик, а оставшиеся нерабочие — визуально отделить (как Portfolio · скоро в сайдбаре, это сделано правильно). Сейчас пользователь не может отличить работающую кнопку от макета.
Дать полям настроек name и перестать отправлять весь payload при сохранении одной карточки. До этого экран настроек лучше пометить как нередактируемый — риск потери конфигурации реальный.
Заменить except Exception на проброс причины. Диагностика уже посчитана слоем данных, её нужно только не потерять.
Удалить дублирующий рендер scope и оставить showGapReportV2 с reason.
Сделать бейджи производными от состояния, а не константами в разметке.
Первые три — не косметика. Пункт 1 может привести к незапланированному импорту, пункт 2 — к потере путей в конфиге, пункт 3 — к тому, что вся работа этой сессии по диагностике не доходит до пользователя.
