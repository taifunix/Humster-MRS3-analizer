## Согласованный целевой порядок

1. **Equity filter (`filter_equity_regime`) — жёстко закреплённый №1.**
2. **Изменённый Lot variant redundancy — №2.**
3. **Единый блок жёстких отсечек — №3: DD >23% при PnL/30д < 3 × DD,
   полный PnL/30 ≤4%,
   либо оба отношения полного/B PnL/30 к полному DD ниже 0.75.**
4. **A/B deterioration — №4.**
5. **Зависимость от топ-5 прибыльных сделок — №5, включён в целевой конфигурации,
   исключение при доле >80%.**

Это решение пользователя заменяет ранее обсуждавшееся предложение переносить
Lot variant после всех фильтров качества. Сейчас в коде порядок обратный:
Lot variant №1, Equity №2. Порядок потребуется согласованно изменить в UI,
серверном effective order, тестах и snapshot-контрактах.
Фиксация позиции Equity сама по себе не определяет обязательность его включения;
изменение enabled/default-on отдельно не согласовано.
Последнее решение переносит A/B с №3 на №4 и топ-5 с №4 на №5.
Позиции начиная с №6 пока не утверждены. Текущий предмет обсуждения —
полный набор фильтров и новые способы сужения выборки.

## Понятные пояснения фильтров в панели

Решение пользователя: для **каждого фильтра** на экране `4. Pareto and filters`
добавить понятное пояснение логики в **существующее поле под названием**.

- Кратко описать, что оценивается и при каком условии стратегия исключается;

  настроек; проверять это при реализации. Пояснения новых согласованных правил

## Lot variant redundancy: согласованное направление

- [x] Проверен текущий выбор: последовательное сравнение DD5, capital,
  robust PnL, DD, PF и ID; это не Pareto dominance.
- [x] Разобрана группа 16871 / 16872: текущий фильтр исключает EQUAL 16871
  за выигрыш INCOME по PnL DD5 всего около 3.82%, при росте DD около 26.95%
  и ухудшении обычного PnL B/30 около 15.78%.
- [x] Пользователь задаёт предпочтение равномерным лотам при сопоставимых
  результатах. Неравномерный вариант должен доказать существенное преимущество.
- [x] Исследованы пороги на двух случайных непересекающихся выборках.
- [x] Записать целевые пороги **10% преимущества PnL DD5 и 10% допуска DD**,
  с двумя проверками B ниже; прежний предложенный порог доходности 15% заменён.
- [ ] Обновить active-spec до изменения поведения, реализовать и проверить
  после завершения согласования оставшихся случаев. Runtime пока прежний.

Для однозначной замены EQUAL неравномерным вариантом при сопоставимых
настройках, периоде, стартовом балансе и суммарном лоте нужны одновременно:

1. `full_dd5_INCOME >= full_dd5_EQUAL * 1.10`.
2. `full_dd_INCOME <= full_dd_EQUAL * 1.10`.
3. `b_dd5_INCOME >= b_dd5_EQUAL`.
4. `b_pnl30_INCOME >= b_pnl30_EQUAL`.

Здесь `full_dd5 = full_pnl30 * 5 / full_dd`,
`b_dd5 = b_pnl30 * 5 / full_dd`; коэффициент приведения одинаков для полного
периода и B одной стратегии. Проценты допуска относительные, не процентные
пункты. Это расчётные proxy, не результат нового DD5 tick-test.
Правило относительного преимущества исследовано для положительных baseline
full/B EQUAL; для неположительных значений автоматическое применение этой
формулы не согласовано. PF не должен заменять эти обязательные условия.

Если первые три условия выполнены, но обычный PnL B ниже, сохранять оба
варианта для следующих фильтров. В остальных случаях окончательная политика
«оставить только EQUAL / сохранить оба» ещё требует обсуждения. Также нужно
определить поведение без EQUAL, с несколькими INCOME, неполными метриками и
округлением равных лотов (у 3ORD последний лот отличается на 1e-12).

Последнее уточнение пользователя 2026-10-01 заменяет эту незакрытую политику:
при полной однозначной паре EQUAL/INCOME, если INCOME не выполнил **любое**
из четырёх условий, оставить только EQUAL. При нехватке фактов оставить оба.
Неоднозначные группы (нет единственной пары EQUAL/INCOME) пока не сокращать;
сравнение равных лотов учитывает допуск `1e-9`. Полный контракт реализации —
в [новой спецификации](../../specs/2026-10-01-performance-v2-filter-sequence.md).

## A/B deterioration: согласованная доработка

Позиция №4 (после последнего уточнения порядка) и следующие правила согласованы пользователем 2026-10-01.
Реализация пока не начата.

### Текущий runtime до изменений

Проверено по текущим коду и конфигу:

- A: доступная история до последних 14 дней; B: последние 14 дней отчёта,
  а не последние 14 дней относительно сегодняшней даты.
- Доходность геометрически приводится к 30 календарным дням; частота сделок
  также приводится к 30 дням. DD5-нормализации в этом фильтре нет.
- При наличии всех пяти обязательных метрик исключение происходит по OR:
  `B_pnl30 <= 5`, либо `A_pnl30 > 0 and B_pnl30 <= A_pnl30 / 10`,
  либо `B_win_rate < 58`, либо `A_trades30 > 0 and B_trades30 <= A_trades30 / 7`.
- Недостаток хотя бы одной метрики отключает все четыре проверки для строки:
  `AB_NOT_EVALUATED_INSUFFICIENT_DATA`; стратегия остаётся на следующих стадиях.
- Win Rate использует прибыльные / (прибыльные + убыточные) завершённые циклы;
  нулевые результаты в знаменатель Win Rate не входят. Минимального числа
  сделок для применения порога Win Rate в самом фильтре нет.
- Это проверка отдельной стратегии, без сравнения с соседями; выбор scope
  `pair_side` / `pair_side_timeframe` не меняет перечисленные условия.
- Фильтр включён по умолчанию. Действующий JS ставит его на позицию №6,
  после Lot, Equity, holding, low trades и min shift; позиция подвижная.
- Подпись `PLANNED` / «Планируемая проверка» в HTML устарела: runtime работает.
- Причина исключения общая `AB_DETERIORATION`, конкретное сработавшее условие
  не выделяется. Изменения порогов, аудита причин и подписи обсуждаются отдельно.

### Целевые правила после уточнений пользователя

Периоды прежние: A — история до последних 14 дней, B — последние 14 дней
отчёта. `A` и `B` ниже обозначают обычный PnL соответствующего периода,
геометрически приведённый к 30 календарным дням, без DD5.

Исключать при выполнении хотя бы одного доступного условия:

```text
B <= 4
OR (A > 0 AND B <= A / 10 AND B <= 15)
OR (completed_trades_B >= 25 AND win_rate_B < 55)
```

- Абсолютный минимум: `B > 4%`; ровно 4% не проходит.
- Падение на 90% или больше сохраняется, но при `B > 15%` эта конкретная
  причина исключения не действует. Ровно 15% исключается только при
  выполнении условия падения; сам по себе B=15% не является нарушением.
- Новый Win Rate: ниже 55% исключает только при 25 и более фактических
  завершённых сделках в B. Это не `Trades/30`: нужно передать существующий
  `WindowMetrics.trade_count` периода B в кандидат. При числе сделок меньше
  25 проверка Win Rate не оценивается и не исключает стратегию; проверки
  доходности продолжают действовать независимо. Ровно 25 сделок активируют
  проверку, ровно 55% её проходят. Это уточнение пользователя заменяет
  первоначальную границу более 10 сделок.
- Высокий B не отменяет независимую проверку Win Rate.
- Старый безусловный Win Rate 58% и исключение по падению частоты сделок
  удаляются. Нового порога активности не добавлять.
- Каждое условие проверяется по своим необходимым фактам. Неизвестный
  Win Rate не отключает проверку доступного B. Неизвестное значение не
  заменяется нулём; при неизвестном A остаются возможными проверки B и Win Rate.
- Сохранять конкретные сработавшие причины и значения; неполную оценку
  отличать от полного прохождения. Заменить устаревшую подпись PLANNED.
- DD/PF/equity-ранжирование в A/B не добавляются. Ранее предложенное
  исследование порогов относительного падения 50%/70% заменено этим решением.

Будущая проверка должна покрыть границы 4%, 15%, 55%, 24/25 сделок,
падение ровно на 90%, независимость причин и частично отсутствующие данные.
Число сделок следует проверять как фактическое число завершённых циклов;
текущий Win Rate исключает нулевые циклы из своего знаменателя. Эта особенность
должна быть видна в evidence, а не изменяться молча. Порог 25 сделок —
операторская граница применимости, не доказательство статистической надёжности.
Отдельно исследовать NO_TRADES: текущий расчёт может вернуть недоступную
доходность вместо нуля, и менять этот оконный контракт без проверки нельзя.

Порядок Lot №2 перед блоком отсечек №3 и A/B №4 требует отдельно проверить потерю альтернатив:
если выбранный Lot-представитель не проходит следующие отсечки, ранее исключённый EQUAL
сам собой не возвращается. Способ обработки этого случая ещё не согласован;
порядок пользователя этим замечанием не изменяется.

## Устойчивость по времени: убрать фильтрацию, сохранить диагностику

Решение пользователя 2026-10-01:

- Убрать `filter_time_consistency` («Устойчивость по времени») из панели
  и отключить его применение для исключения стратегий. Одного скрытия
  UI-контрола недостаточно: текущий отбор не должен исключать по этой стадии.
- Продолжать рассчитывать последовательные периоды всей истории и сохранять
  результаты независимо от отсутствия фильтра в панели. Сохранить вывод
  `Positive windows` в Excel.
- Исправить логику окон без сделок: подтверждённый `NO_TRADES` не считается
  убыточным окном, не входит в число оценённых окон и не должен приводить
  к FAIL из-за прежнего требования трёх прибыльных из четырёх исходных окон.
  Два прибыльных окна и два окна без сделок отображаются как **2/2**.
- Не смешивать отсутствие сделок с отсутствующими, повреждёнными или
  недоступными метриками. Во втором случае результат остаётся **N/A**;
  если во всех периодах нет сделок — результат не оценён, а не PASS.
- Исторические сохранённые результаты отбора не переписывать. До реализации
  уточнить совместимость старых запросов со стадией и необходимость внутреннего
  PASS/FAIL для диагностического показателя; точный новый порог такого статуса
  пользователь не задавал. Он в любом случае не влияет на исключение.
- При проверке реализации покрыть сохранение расчётов/Excel без UI-фильтра,
  случай 2 прибыльных + 2 NO_TRADES, все NO_TRADES и отсутствующую метрику.

Статус: решение записано для будущей реализации; код пока не изменён.

## Зависимость от одной сделки: исследование топ-5

Пользователь поддержал исследование топ-5 и поручил не учитывать комиссии.
После исследования пользователь утвердил порог **>80%**, включение фильтра
и первоначальную позицию №4; последнее решение переносит его на **№5**.
Сохраняются обсуждавшиеся условия применимости: история
не короче 45 суток и минимум 25 прибыльных завершённых сделок. Ниже этих
границ показывать диагностику без исключения. Ровно 80% проходит.
Ранее предложенный порог 90% остаётся историей обсуждения и не является
целевым порогом. Это решение для будущей реализации; runtime ещё прежний.
Текущий runtime остаётся прежним: одна лучшая сделка / сумма положительных
PnL, минимум четыре прибыльные сделки, порог 35%, либо неположительный
остаток после удаления одной лучшей сделки.

### Проверенная гипотеза

- Надёжно восстановленные завершённые циклы, история не короче 45 суток,
  минимум 25 **прибыльных** завершённых сделок, положительный суммарный PnL.
- `total = sum(completed_trade_pnl)`, включая убытки;
  `top5 = sum(five largest positive completed_trade_pnl)`.
- `share = top5 / total * 100`, `remaining = total - top5`.
- Исследуемое исключение: `share > 70%`; равенство 70% проходит.
- Комиссии не вычитаются. Незавершённый хвост не включается. Знаменатель
  берётся из тех же завершённых циклов, а не из report wallet/total PnL.
  Неположительный total не получает фиктивной доли; его правило нужно
  отдельно определить при согласовании окончательного контракта.

## Следующий шаг

### Исследование сравнительного отбора и ранжирования в Excel

Пользователь перешёл к отбору после пяти согласованных фильтров и поручил
собрать исследовательский Excel с реальными стратегиями, изменяемыми допусками
и сразу видимым результатом. Начать со сравнения внутри пары + стороны + ТФ,
отдельно по числу ордеров; затем выбирать представителей ТФ и сравнивать ТФ.

Принятые направления:

- После допуска по B PnL/30 и полному PnL/30 средняя по доходности стратегия
  сильной группы может выигрывать у её лидера благодаря лучшей конструкции.
  Более высокий PnL не даёт безусловной защиты от такого выбора.
- Даже относительная разница DD в 20% сама по себе не должна решать исход.
  В прототипе 8% против 9.6% — пример этой границы, не разница в 20 п.п.
- Больший Shift получает реальное предпочтение при близких прочих показателях,
  включая DD; это не только сортировка отображения. Для первого исследования
  явно использовать Shift первого ордера, остальные показывать отдельно;
  обобщение предпочтения на вектор Shift ещё не согласовано.
- Плато сравнивать по соответствующим ордерам: допустим небольшой проигрыш
  по одному при заметном выигрыше по другому; сумма не скрывает слабый ордер.
- Open MA и Close MA участвуют в сравнении только внутри одного ТФ.
- Сначала работать на реальных примерах в Excel. Окончательные допуски,
  правила сравнений разных ORD/ТФ и итоговое ранжирование ещё не утверждены.

Последнее уточнение пользователя: основа исследования — несколько торговых
пар, выгруженных стандартным экспортом панели. Вычисления выполнять отдельным
Python-обработчиком; Excel служит для просмотра и ручных решений. Прототип
с большим числом Excel-формул отложен. Объединённый входной файл проверен ниже;
новые вычисления фильтрации и ранжирования ещё не реализованы.

Предлагаемый рабочий цикл: исходная выгрузка → изменение допусков на простом
листе «Настройки» → запуск обработчика → новый результат Excel. Лист настроек
содержит только значения; формулы ранжирования живут в Python. Сохранять
стандартные колонки, добавлять экспериментальные статус, ранг, причину,
ID предпочитаемой альтернативы и изменение ранга относительно прошлого
прогона. Исходник сохранять отдельно, ручные решения переносить по ID и
Result ID. Конкретный алгоритм общего ранжирования ещё предстоит согласовать.

Пользователь предоставил шесть стандартных выгрузок в локальной папке
`Output/FilterExp` и разрешил использовать действующий отбор панели без
воспроизведения запланированных пяти фильтров. Объединить их в одну книгу:
`Finalists` — текущая рабочая выборка, `All candidates` — все исходные строки,
отдельные вкладки прошедших стратегий по парам и сводка источников.
Сохранять метрики, оформление, ручные поля и происхождение каждой строки;
объединённая исследовательская книга не является workbook для review-import.
Новые фильтры при объединении не применять. Пары/стороны сравнивать независимо.

Уточнение пользователя заменяет прежнее упоминание «трейдов плато»:
имеется в виду **Trades/30**, частота сделок готовой стратегии за 30 дней.
Этот показатель уже есть в стандартном XLSX. `plateau_total_trades` в
эксперимент не включать и специально из базы не подгружать.

#### Архитектура обработчика для последующего подключения к панели

Пользователь требует переиспользовать будущую расчётную логику в фильтре
панели. Уточнение пользователя: переносится **только логика отбора и
ранжирования**. Будущий фильтр работает как существующие фильтры панели:
получает факты из базы, применяет настройки и передаёт результат обычному
экспорту. Готовый Excel выгружается после расчёта, как сейчас.
Чтение и редактирование исследовательских Excel из панели в задачу не входят.

Два способа использования общей логики:

- Исследование: выгрузка Excel → Python-расчёт → Excel для сравнения результатов.
- Панель: данные базы → тот же алгоритм в pipeline фильтров → готовая выгрузка Excel.

Разделить только необходимые обязанности:

1. Excel-адаптер читает стандартные колонки, включая составные Points/MA,
   сохраняет ID, Result ID, источник и получает обычные числовые значения.
   Не восстанавливать точные даты из отображаемых Start/End без года.
2. Расчётное ядро принимает нормализованные записи и настройки и возвращает
   решения, причины, сравниваемые ID и ранги. Оно не открывает Excel/БД,
   не зависит от локальных путей, русских заголовков листов или UI.
3. Исследовательский Excel-адаптер записывает результаты и настройки эксперимента.
   В будущем pipeline панели вызывает расчётное ядро напрямую на фактах из базы;
   существующий экспорт записывает уже рассчитанный результат.

Использовать существующие внутренние имена метрик и типы там, где они подходят;
не копировать алгоритм отбора отдельно для панели и Excel. До реализации
каждого правила закрепить его контракт и проверить совпадение результата
для одинаковых нормализованных данных из обоих источников. Ранги разных
пар не сопоставлять. Отсутствующие метрики не превращать в нули.
Текущая задача объединения готовит вход; новый алгоритм ещё не утверждён.

#### Первый вычислительный эксперимент: нижняя граница PnL

Пользователь разрешил начать работу на объединённой книге. Первый эксперимент
реализует только допуск по обычным B PnL/30 и полному PnL/30 внутри
пары + стороны + ТФ. Расчётная функция не зависит от Excel и базы. Код пока
исследовательский; после выбора правил эту функцию можно перенести в модуль
панели без переноса файлового процесса.

- Режим adaptive: отдельно по каждой доступной метрике сортировать исходную
  группу, взять верхние ceil(N/2) значений и их медиану; граница равна
  медиане, умноженной на настраиваемую долю. Первые пробы 0.60/0.70/0.80;
  основной пробный вариант 0.70 для обоих PnL, не утверждённый порог панели.
- Режим half: граница — последнее значение верхних ceil(N/2); равные значения
  на границе сохраняются. Режим off отключает дополнительный отсев.
- Последнее уточнение пользователя: основной порядок **последовательный**,
  сначала B/30 на исходной группе, затем полный PnL/30 на её оставшихся
  стратегиях. Строки с недоступным B сохраняются для второго шага с N/A.
  Исключённые по B на втором шаге не оцениваются и не участвуют в его ориентире.
  Прежний вариант двух независимых границ по исходной группе сохранить как
  `parallel` для сравнения: пользователь также поручил посмотреть его результат.
  В настройках `pipeline=sequential` основной, `parallel` альтернативный.
  Оба варианта проверять на одной исходной выборке и с одинаковыми долями.
  Равенство любой применимой границе проходит.
- Missing не заменять нулём. При отсутствии метрики или неположительном
  ориентире adaptive соответствующая оценка недоступна. Известное нарушение
  второй метрики всё равно исключает; иначе строка остаётся с пометкой N/A.
- В Excel хранить настройки как значения, без расчётных формул. Исходный
  Finalists остаётся неизменным набором для каждого повторного прогона.
  Новая книга сохраняет все строки с результатом/причиной и сводками по ТФ;
  старую книгу не перезаписывать. Настройки нового прогона пользователь меняет
  в последней книге, затем запускает локальный обработчик.
- Уточнение интерфейса эксперимента: основной рабочий лист — **Finalists**
  со всеми парами после текущих фильтров панели. В нём добавить отдельные
  сигнальные колонки «Отбор B/30», «Отбор PnL/30», «Итог PnL» для обычного
  автофильтра Excel. Значения ДА/НЕТ/N/A; второй шаг для B failures —
  «ПРОПУЩЕН». Рядом границы и причина, плюс итоги обоих вариантов для сравнения.
  Исходные колонки, ручные данные и строки сохранить; новые сигналы обновляются
  при каждом запуске. Книгу открывать на Finalists, автофильтр охватывает сигналы.
- Последнее уточнение просмотра заменяет сложную книгу со сводками:
  предоставить **только три листа 60%, 70%, 80%**, на каждом все исходные
  1903 Finalists, стандартные поля и три сигнала в начале (B, full, итог).
  Расчёт sequential для всех трёх; без настроек, прочих сводок и новых рангов.
  Пользователь просмотрит три листа перед выбором дальнейших правил.
- Последнее изменение алгоритма: считать PnL-допуск **внутри пары в целом,
  объединяя ТФ**. Стороны остаются раздельными (`symbol + side`). Порядок B ->
  full на оставшихся и три сценария сохраняются. Предыдущие расчёты по ТФ
  являются историческим сравнением; новый основной файл — вариант по парам.

### Жёсткие отсечки: уточнения пользователя

- На первом исследовательском этапе предложена одна общая стадия с независимыми
  проверками по OR и конкретными причинами исключения, без Pareto/доминирования.
  Последние согласованные порядок и пороги приведены ниже; ранние предложения
  в этом подразделе сохраняются как история исследования.
- Принят full DD максимум 25%: исключать при `full DD >25%`, ровно 25% проходит.
- Принят минимум **полный PnL/30 >3%** (пользователь отдельно уточнил /30,
  не общий PnL истории): исключать при `full PnL/30 <=3%`. Пользователь отдельно
  уточнил: применять **ко всем с известным PnL/30**, без guards возраста/сделок.
  Недоступная доходность не получает ложного нулевого значения.
- Доходность/DD и PF — исследовать на реальной базе с лучшими исключаемыми
  примерами; окончательные пороги не утверждены.
- Худшая отдельная потеря спорна: не включать в целевые отсечки.
- Длительное невосстановление и концентрация в одной неделе — проверить числа,
  примеры и пересечение с Equity до решения о включении.

#### Окончательное уточнение пользователя: 23 / 4 / 0.75

Последнее решение заменяет DD25, full/30>3 и исследовательское предложение ratio0.5.
В единой стадии независимых жёстких отсечек исключать по OR:

```text
full_DD > 23 AND full_PnL/30d < full_DD * 3
OR full_pnl30 <= 4
OR (full_pnl30 < 0.75 * full_DD AND B_pnl30 < 0.75 * full_DD)
```

DD-ветка требует оба валидных показателя: DD и full PnL/30d.
Самостоятельная full PnL/30 ветка проверяется при наличии этого показателя.
Ratio сохраняет условия применимости исследованного варианта: >=45 суток,
>=25 надёжно завершённых сделок, известные full/B returns и full DD>0.
Ровно DD23 проходит; ровно full PnL/30=4 не проходит; равенство ratio0.75
не исключает по ratio. Причины проверять независимо, missing не заменять нулём.
Последующее уточнение пользователя от 2026-10-01 меняет **только ветку DD**:
`full_DD > 23 AND full_PnL/30d < full_DD * 3`. `GYK30l` в сообщении
означает `ПНЛ30д`, то есть полный PnL/30d. При равенстве `3 × DD` эта ветка
не исключает; неизвестный PnL/30d не создаёт ложного DD-исключения.
Остальные ветки OR не меняются. Контракт реализации:
[новая спецификация](../../specs/2026-10-01-performance-v2-filter-sequence.md),
[ADR-0053](../../decisions/0053-performance-v2-dd-profit-guard.md).
PF, невосстановление, прибыль одной недели и худшую отдельную потерю
**не добавлять** в эту стадию. Последним решением ей назначена **позиция №3**,
после Equity и Lot variant, перед A/B и топ-5.

#### Автоматический REJECTED от блока №3

Пользователь поручил сохранять в базе **User Status = REJECTED (кандидат на удаление)**
для стратегии, фактически исключённой единым блоком жёстких отсечек.
Пользователь отдельно подтвердил поле **User Status**, исправив первоначальное
упоминание User Rank. Это не обычный временный FILTERED результата отбора.
В текущем data contract REJECTED соответствует устойчивой отметке `strategy_tags`;
числовой User Rank не менять.

- Отметка относится только к известному нарушению правила включённого блока №3;
  пропущенная оценка или исключение другим фильтром её не создаёт.
- Хранить причину/значения, конфигурацию и ссылку на результат отбора; отличать
  автоматическое происхождение от ручного review. В базе и Excel отображать
  эффективный статус REJECTED, включая случай более раннего ручного статуса.
- Кандидат на удаление остаётся в базе; физическое удаление не выполняется.
  Отключение фильтра само по себе не снимает отметку. Ручное изменение статуса
  сохраняется как явный способ снять REJECTED.
- Точный момент записи при выполнении отбора (preview или сохранение результата)
  закрепить в active-spec до реализации; запись и соответствующее evidence
  должны публиковаться атомарно, с проверкой актуальности результата.

Решение о новом источнике REJECTED записано в
[ADR-0052](../../decisions/0052-performance-v2-hard-cutoff-rejected.md).
Текущая база не изменялась; исследовательские списки не импортируются как REJECTED.

Совместный эффект на сохранённой reference-выборке после Equity/current Lot/
согласованного A/B/топ-5: 9 958 -> **8 654**, исключаются **1 304** уникальных
стратегии. Независимые причины: DD23=988, full/30<=4=38, ratio0.75=468;
с учётом пересечений последовательный вклад 988+38+278=1 304.
Это пересчёт сохранённого снимка, не новый live preview и не simulation revised Lot.
Целевой runtime ещё не внедрён. Эти 1 304 — исключения после всех четырёх
исследованных фильтров, а не число будущих REJECTED на новой позиции №3:
блок теперь оценивается до A/B и топ-5, и этот префикс требует отдельного подсчёта.

Исследование завершено в
[отчёте независимых отсечек](../../reports/2026-10-01-performance-v2-hard-cutoff-research.md).
Проверка 30 940 ACTIVE, у 25 950 свежие Equity/window caches; baseline после
Equity/current Lot/new A/B/top5 — 9 958. DD25 исключает 790, принятый full/30>3
ещё 10; остаётся 9 158. Ratio0.3/0.5/0.75 дополнительно исключают 3/74/291.
PF<1.1/1.2/1.3 добавляет 0/2/9; лучший PF<1.3 пример имеет full/30=25.89%,
B/30=18.17%, DD=21.65% и поэтому не назван очевидным мусором.
Recovery нашёл 57, 54 уже BLOCK Equity; остальные три исключаются другими
правилами, после DD25 новых нет. Weekly<=0: 109, все уже BLOCK Equity;

20 примеров подтверждены независимым raw action/equity пересчётом.
Предложение root: одна стадия DD25/full30>3, рассмотреть ratio0.5; PF/recovery/

Полный набор 24 stage IDs, оба final ranking и предложения разобраны в
[отчёте по всем фильтрам](../../reports/2026-10-01-performance-v2-filter-inventory.md).
Подтверждены 0%-tolerance fallback bug и взаимное исключение отрицательных
DD5 в plateau multiplier; runtime пока не исправлялся. Исследовательские
приоритеты: доходность относительно DD, вариант вместе с Holding,

позднее уточнены выше: ratio0.75 принят, PF не добавлять, DD23 и full/30>4
заменяют DD25/full/30>3. Номера начиная с №6 не утверждены. При >80% из прежних 70 прошедших
Equity/current Lot/new A/B примеров исключаются 30; revised Lot не симулирован.

Уточнение пользователя: сейчас обсуждать только **жёсткие отсечки по собственным
показателям стратегии**, существующие либо новые. Разбор/критика старых фильтров,
Pareto и отбор через доминирование отложены до отдельного обсуждения.
Новые правила не должны зависеть от квартилей, ранга или качества соседей.
Принятый блок жёстких отсечек определён выше последним решением 23/4/0.75;
прочие варианты не включать. Номера после №5 ещё не утверждены.

Выбрать следующий критерий жёсткой отсечки; при подготовке реализации проверить
граничные случаи согласованного A/B и взаимодействие с Lot №2.
Не трактовать запись решений как выполненное
изменение runtime или разрешение нового tester run.
