# Проверка данных финалистов для нормализации sizing

Дата: 2026-09-13. Read-only исследование, без изменения PerformanceDB,
импорта, запуска tester или реализации нового алгоритма.
Контекст: [черновик поиска, разделы 3 и 5](2026-09-12-portfolio-optimizer-weighted-search-discussion.md).

## Результат

База доступна и пользовательские финалисты сохранены. Для циклов, длительностей
и исходной equity данные есть. **Подтверждённой нормализации расчётной полной
позиции на USDT только из текущих typed-полей пока нет.** В исходном HTML есть
цена и стоимость исполнения, которые нынешний импорт не сохраняет. Эти поля
позволяют проверить стоимость фактических исполнений, но ещё не доказывают
плановый размер всех открывающих уровней не полностью набранной позиции.

## Объём проверки

- Текущие решения получены через существующие `latest_user_reviews_by_strategy`
  и `effective_selection_decisions`, пересечение ручного и действующего FINALIST.
  Не использовалась дата последнего импорта review как обязательный gate.
- 21 активная стратегия, 15 пар, все LONG, текущий результат есть у каждой.
- Общий период по метаданным: 2026-07-30 00:00 UTC — 2026-08-28 00:00 UTC,
  29 дней; индивидуальные сохранённые интервалы 29–70 дней. Это ещё не
  утверждение непрерывного покрытия equity каждого календарного момента.
- Прочитаны 12 231 действие и агрегаты/ряды 97 179 equity samples.
  Из действий выделены 2 582 завершённых цикла за индивидуальные периоды.
  Нарушений проверяемой последовательности opened → … → flat не найдено;
  у всех последняя сохранённая позиция закрыта. Это не полный аудит каждого
  торгового/импортного инварианта.
- Целиком в общее окно входят 1 626 циклов; на стратегию от 5 до 333.
  Минимум: TQQQ 2h и UVXY 1h по 5, QNTX 15m — 7. Короткую выборку показываем,
  не вводим новый произвольный порог исключения финалистов.
- Пять стратегий имеют позицию через начало общего окна, шесть — через конец.
  При подготовке общей equity нельзя обрезать всё к индивидуальным flat-окнам.
- Медианный промежуток между equity samples по разным стратегиям 60–180 секунд;
  наличие более длинных разрывов не интерпретировано автоматически как потеря
  данных: источник событийный. Для нормализации нескольких циклов внутри
  промежутка нужна отдельная проверка их разделимости по сохранённым значениям.

## Сопоставление с исходными HTML

По именам финалистов в активном каталоге отчётов найдены 13 HTML. Поиск просмотрел
2 533 файла соответствующих пар/таймфреймов в 16 потоков. Это не поиск по всем
возможным дискам/архивам; отсутствие оставшихся восьми здесь не означает их
окончательную утрату. Другие имена при одинаковой typed identity этим поиском
также не исключены.

Для всех найденных 13:

- SHA-256 присутствует в `import_files`.
- Все сохранённые действия совпадают с HTML по исходному action_index,
  времени UTC и денежным/размерным полям с допуском 1e-12.
- Все сохранённые wallet/equity совпадают по времени и значениям: максимальное
  расхождение 5e-13, в пределах DECIMAL(38,12).
- Для всех исходных действий `Cost = abs(Size) × Price`.
- Настройки: use_upnl=true, use_frozen_balance=true, use_fix=false,
  balance_percentage_long=100, risk_long=1, max_balance=0; leverage=20.
  Настройки именно этих исходных отчётов, не текущие биржевые ограничения.

Пример BABA 3h, strategy_id=16618, result_id=16767: первое открытие
2026-07-06 01:36 UTC — Size=9,6, Price=94,63, Cost=908,448 USDT.
Size здесь количество актива, а не USDT. Позиция закрывается двумя исполнениями
9,31 и 0,29. При lot_x=1 и начальном банке 1000 фактическая стоимость первого
входа не равна 1000. Нельзя без проверки подменять стоимость исполнения
стартовым банком либо выдавать её за плановую ёмкость всех уровней стратегии.

У шести найденных HTML начальные действия исключены текущим импортом:
PANW 3h — 10, TTWO 2h — 35, SNOW 1h — 69, SNOW 45m — 83,
TSEM 45m — 117, NVDL 15m — 180. Действия БД совпадают с оставшейся частью,
это не расхождение результатов. У NVDL первое сохранённое открытие следует
при балансе до комиссии около 1101,923 USDT, хотя поле initial_balance=1000
относится к исходному отчёту. Аналитика должна учитывать фактическую границу
сохранённого окна. В первом исследовательском подсчёте база первого цикла была
ошибочно взята как initial_balance; локальный audit исправлен на явно помеченную
оценку `balance - action pnl + fee`. Это не универсальное восстановление sizing.

## Что текущая БД не сохраняет

У всех 12 231 проверенного действия raw_action_json=NULL. В typed actions
нет Price/Cost. Код импорта явно пишет None в raw_action_json; отсутствие
дополнительных полей здесь не является повреждением БД.

`strategy_results.commission_rate` сохраняет TakerFee. В найденных отчётах
наблюдаются отношения Fee/Cost как 0,00001, так и 0,0002. Поэтому восстановление
стоимости как Fee / единственный commission_rate будет ошибочным; при нулевой
комиссии оно вообще невозможно. Такой fallback не использовать.

Схема стратегии содержит MA, shift и lot_x, но не полный снимок параметров
UPNL/frozen/sizing/max_balance из конкретного отчёта. Существующий JSON экспорта
не следует автоматически считать настройками текущего результата. Один JSON
BABA прочитан после разрешённого read-only снятия sandbox-ограничения; первичным
доказательством в этой проверке служат сопоставленные HTML.

## Следствие для плана

1. Сохранить существующую БД и ручные статусы. Данные пригодны для исследования
   циклов и equity. Последующее решение пользователя: для текущих 21 финалиста
   подготовить новые отчёты вместо дальнейшего поиска старых источников.
2. При реализации подготовки данных расширить typed-хранение необходимыми
   фактами: цена/стоимость исполнения и минимальный снимок параметров sizing
   конкретного результата. Контракт новых полей, версия и миграция — отдельная
   задача, старые записи не заполнять придуманными значениями.
3. Рассмотреть однократное дополнение из сохранившихся HTML после проверки
   identity, исходных индексов/времён, периода и соответствия текущим фактам.
   Найденные 13 отчётов дают исходный материал; запись в БД этим исследованием
   не выполнена. Проверка одного hash без соответствия текущему результату
   недостаточна из-за сохранения result_id при REPLACE.
4. До выбора знаменателя S_i,k проверить на 1ORD и многоуровневой стратегии,
   можно ли восстановить плановый полный sizing и момент выставления ордеров.
   Price/Cost подтверждают исполнение, не источник пересчёта неисполненных
   ордеров. Если нужен приближённый знаменатель, явно задать его семантику
   и проверить влияние на рейтинг; не называть его точным восстановлением.
5. Повторно читать HTML в каждом портфельном расчёте не требуется: после
   однократной подготовки используются проверенные производные данные и кэш.

## Совместимость разового обновления после нового ретеста

Пользователь выбрал новые отчёты всех 21 финалиста; восстановление старых
источников больше не является текущим путём. Решение и отдельная будущая задача
автоматического сохранения полей импортёром записаны в разделе 3.1 черновика.

Проверено на временных DuckDB существующими тестами, без изменения runtime:
добавление nullable `strategy_results.optimizer_source_metadata_json VARCHAR`
с сохранением schema_version=4 проходит текущий validator и повторную
инициализацию. Семь проверок прошли: многопоточный ADD нескольких стратегий;
идемпотентный ADD и запрет подмены; REPLACE с проверкой mapping/typed identity;
замена scoped children; откат при ошибке публикации; запрет сокращения периода;
сохранение пользовательских решений после обычного анализа и REPLACE.
Результат: **7 passed, 1 warning**, 12,29 секунды, 20 инициализаций расширенной
схемы. Предупреждение — существующий pandas FutureWarning в тесте review.

Первый запуск через stdin не прошёл из-за Windows multiprocessing spawn:
дочерний процесс не может открыть `<stdin>`. Повтор из обычного файла с
`if __name__ == '__main__'` прошёл. Локальная воспроизводимая команда:
`.venv/Scripts/python.exe Output/research/compatibility_probe.py`;
вывод — `Output/research/compatibility-probe.txt`. Это одноразовые исследовательские
артефакты, не реализация загрузчика.

Ограничения проверенного решения: каталог таблиц v4 фиксирован, новые таблицы
старый validator не принимает. `connection.append` для действий позиционный:
добавление новых колонок действий несовместимо с неизменённым импортом.
Поэтому Price/Cost предлагается сохранять в существующем raw_action_json.
Дополнительная колонка результата требует проверки ревизии при чтении:
старый REPLACE её не очистит. Успех тестов не доказывает готовность этой проверки
или корректность будущего дополнения из HTML. Рабочая БД не мигрировалась;
загрузчик, проверка на копии и новые 21 отчёт ещё не подготовлены в этом исследовании.

Подробные числовые результаты сохранены локально в
`Output/research/2026-09-13-finalist-sizing-audit.json`; это generated artifact,
не часть runtime и не предназначен для коммита. Исследование выполнено через
`.venv/Scripts/python.exe` и DuckDB `read_only=True`.
