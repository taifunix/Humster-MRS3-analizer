# Бриф на исследование: частота сделок и качество точек MRS2

> Это задание для отдельного агента на машине с большим объёмом данных.
> Контекста предыдущих обсуждений у него нет — бриф самодостаточный.

## 1. Контекст

Ты анализируешь результаты бэктестов торговой стратегии MRS2 (одноордерная
база, из которой затем собираются многоордерные MRS3-стратегии). Одна
«точка» = один прогон бэктеста с фиксированной комбинацией параметров:

| Параметр | Значения |
| --- | --- |
| `symbol` | торговая пара, например `MSTRUSDT` |
| `side` | `LONG` или `SHORT` |
| `timeframe` | `5m, 15m, 30m, 45m, 1h, 2h, 3h, 4h` (8 значений) |
| `shift_bp` | 30, 40, 50, 60, 70, 90, 110, 140, 170, 200, 230, 270, 310, 350, 390, 430, 470, 510, 550 (19 значений) |
| `open_ma` | длина открывающей MA, 2..7 (6 значений) |
| `close_ma` | длина закрывающей MA, 2..7 (6 значений) |

Полная сетка = 19 × 6 × 6 × 8 = **5472 точки** на пару и сторону.

Механика входа: лимитный ордер выставляется со сдвигом относительно
скользящей средней. Для LONG множитель < 1 и
`shift_bp = round((1 − multiplier) × 10000)`. Для SHORT множитель > 1 и
`shift_bp = round((multiplier − 1) × 10000)` — внимание, в SHORT-конфигах
множитель записан строкой с **запятой** как десятичным разделителем
(например `"1,003"`), перед разбором заменить запятую на точку.

Зачем это нужно: проверяются две вещи — (а) корректность фильтра
минимального числа сделок, который сейчас задан разделимой формулой
`базовая_частота(ТФ) × коэффициент(сдвиг)`, и (б) возможность улучшить
дешёвый «скринер», который по подсетке из 304 точек пытается предсказать,
стоит ли пара полного прогона на 5472 точки.

**Важно: не подгоняй результат под ожидания.** Ниже сформулированы гипотезы,
но твоя задача — честно их проверить, в том числе опровергнуть. Отрицательный
результат так же ценен, как положительный.

## 2. Где брать данные

Порядок приоритета источников:

1. **`*.surface-v6.duckdb`** — лучший источник. Таблица
   `point_analysis_input` с колонками `scope_key`, `point_id`, `row_json`.
   В `row_json` лежит JSON с полями: `symbol, side, timeframe, shift_bp,
   open_ma, close_ma, pnl_pct, dd_pct, trades, wins, losses, win_rate_pct,
   profit_factor, events_last_30d`. Одна строка = одна точка полной сетки.
   Окно теста — в таблице `scope_manifests`, поле `witness_json` содержит
   `start` и `end`.
2. **`reports_history.csv`** (и партиции `reports_history_p*.csv`) из папок
   отчётов тестера. Все файлы в одной папке читаются и объединяются как один
   набор. Колонки метрик: `TotalPnLPercent, MaxDrawdownPercent, TotalTrades,
   WinRate, ProfitFactor, StartDate, EndDate`. Колонки параметров:
   `settings[*].basic.symbol`, `settings[*].basic.time_frame`,
   `settings[*].mrs2.ma_long.len`, `settings[*].mrs2.ma_close_long.len`,
   `settings[*].mrs2.ma_long.multiplier` (для SHORT —
   `ma_short.len`, `ma_close_short.len`, `ma_short.multiplier`).
3. **`strategy_performance.duckdb`** (PerformanceDB) — если найдёшь, это
   самый ценный источник: в нём результаты реально протестированных
   MRS3-стратегий, то есть независимая «истинная метка» качества пары.
   Обязательно проверь наличие и сообщи, есть он или нет.

**Не трать время на `*.analysis-v6.duckdb`** — там только пост-обработанные
структуры, плато и по одной «базовой» точке на скоуп; сырой сетки с PnL/DD
по всем точкам в них нет (проверено).

**Режим строго read-only.** Ничего не писать в базы, не менять код, не
запускать тестер, не публиковать surface.

## 3. Обязательные определения

Используй строго эти формулы, иначе результаты нельзя будет сопоставить.

```
effective_days = (window_end − max(window_start, listing_date)) в днях
pnl30          = pnl_pct × 30 / effective_days
efficiency     = pnl_pct / dd_pct
trades_per_day = trades / effective_days
```

- Если дата листинга пары недоступна — используй полное окно и **явно
  пометь** такие пары в отчёте.
- Точки с `effective_days ≤ 0` исключай.

`economic_pass` = все условия одновременно:
```
dd_pct > 0
pnl_pct        >= economic_min_pnl_pct
win_rate_pct   >= economic_min_win_rate_pct
dd_pct         <= economic_max_dd_pct
efficiency     >= economic_min_efficiency
trades         >= absolute_floor          (см. ниже)
```
`absolute_floor` = `absolute_floor_at_or_below`, если
`shift_bp <= absolute_floor_boundary_bp`, иначе `absolute_floor_above`.

**«Хорошая точка»** = `economic_pass` **и** `pnl30 >= 10`.

Все пороги (`economic_min_pnl_pct`, `economic_min_win_rate_pct`,
`economic_max_dd_pct`, `economic_min_efficiency`, `absolute_floor_*`,
`base_rate_tf`, `shift_factors`) бери из локального `config.local.json`
и **обязательно приведи их фактические значения в отчёте** — если они
отличаются от моих, расхождения в результатах нужно будет отнести на конфиг,
а не на данные.

## 4. Что исследовать

### Блок A — взаимодействие «таймфрейм × сдвиг» (приоритет 1)

Гипотеза к проверке: зависимость частоты сделок от таймфрейма **меняет
направление** в зависимости от сдвига. На малых сдвигах младшие ТФ дают
больше сделок, на больших — старшие. На выборке из 8 пар разворот
наблюдался на 170–230 bp.

Посчитать:
1. Медиану `trades_per_day` в разрезе `timeframe` × `shift_bp` (таблица
   8 × 19), пулом по всем парам, отдельно для LONG и SHORT.
2. Отношение `trades_per_day(5m) / trades_per_day(4h)` для каждого уровня
   сдвига. Указать, на каком сдвиге оно пересекает 1.0.
3. То же отношение и точку разворота **отдельно для каждой пары** — насколько
   стабильна точка разворота между парами? Дать разброс (min/median/max).
4. Проверить, меняется ли картина между LONG и SHORT.

### Блок B — какая форма модели описывает данные (приоритет 2)

Текущая модель разделима: `ожидаемые_сделки/день = base_rate(ТФ) ×
shift_factor(сдвиг)`. Такая форма жёстко фиксирует постоянное отношение
между таймфреймами на всех сдвигах.

Посчитать:
1. Насколько велика ошибка разделимой модели: для каждой ячейки
   ТФ × сдвиг сравнить фактическое отношение к 4h с тем, которое
   предполагает `base_rate(ТФ)/base_rate(4h)`. Дать таблицу отношений
   факт/модель.
2. Подобрать двухпараметрическую форму `trades_per_day ≈ A(ТФ) ×
   exp(−shift_bp / L(ТФ))` — по отдельной паре (A, L) на каждый таймфрейм.
   Вернуть подобранные A и L и меру качества подгонки (R² или медиану
   относительной ошибки).
3. Проверить, не описываются ли данные лучше чем-то более простым
   (например степенной зависимостью) — если да, сообщить.

### Блок C — что ломает текущий фильтр (приоритет 2)

Фильтр: `required_min_trades = ceil(effective_days × base_rate(ТФ) ×
shift_factor(сдвиг))`; точка отбраковывается, если `trades <
required_min_trades`.

Посчитать:
1. Долю точек, проходящих фильтр, в разрезе ТФ × сдвиг (таблица 8 × 19).
2. Сколько **хороших точек** (по определению из раздела 3) этот фильтр
   отбраковывает — всего и в разрезе ТФ × сдвиг. Это ключевая цифра:
   фильтр не должен убивать экономически состоятельные точки.
3. Проверить границы `shift_factors` на артефакты: есть ли резкие скачки
   доли прохождения на границах диапазонов (например при переходе через
   200 bp), не соответствующие плавному изменению фактической частоты
   сделок?

### Блок D — где на самом деле живут хорошие точки (приоритет 1)

Это самая важная часть для улучшения скринера. Ранее метод скринера
калибровался на выборке, где **низкие** сдвиги давали больше всего хороших
точек (31.7% при 30 bp против 3.3% при 550 bp). На свежей выборке из 3 пар
картина оказалась обратной — все хорошие точки лежали на 430–550 bp.
Нужно понять, что верно на большом объёме.

Посчитать:
1. Долю хороших точек в разрезе `shift_bp` (19 строк), пулом и по парам.
2. Долю хороших точек в разрезе `timeframe` (8 строк). Отдельно ответить:
   есть ли таймфреймы, которые вообще не дают хороших точек?
3. Долю хороших точек в разрезе `open_ma` (6 строк) и `close_ma` (6 строк).
4. Для каждой пары — общее число хороших точек в полной сетке 5472.

### Блок E — работает ли дешёвая подсетка (приоритет 1)

Скринер прогоняет только 304 точки из 5472: `open_ma = 4`,
`close_ma ∈ {2, 6}`, все 19 сдвигов, все 8 ТФ. По числу хороших точек в
этой подсетке он выносит вердикт о паре.

Посчитать:
1. Для каждой пары: число хороших точек в полной сетке (5472) и в подсетке
   скринера (304).
2. Ранговую корреляцию Спирмена между этими двумя величинами по всем парам —
   это главная метрика полезности скринера. Чем больше пар, тем надёжнее.
3. Сравнить с альтернативными подсетками того же размера (~304 точки):
   - `open_ma = 4`, `close_ma ∈ {2, 3}`
   - `open_ma = 2`, `close_ma ∈ {2, 3}`
   - `open_ma = 4`, `close_ma ∈ {3, 6}`
   - случайная выборка 304 точек (усреднить по 20 повторам — как базовый
     уровень «ничего не знаем»)
   Для каждой — та же ранговая корреляция с полной сеткой. Какая подсетка
   лучше?
4. Проверить, можно ли удешевить сетку без потери корреляции: что будет,
   если выбросить 5m (остаётся 266 точек)? А если выбросить таймфреймы,
   которые по блоку D не дают хороших точек?

### Блок F — если нашёлся PerformanceDB (приоритет 1, если данные есть)

Если `strategy_performance.duckdb` доступен, это даёт независимую проверку
против **реальных результатов тестера**, а не против самой же сетки.

1. Для пар, у которых есть и полная сетка, и записи в PerformanceDB:
   построить «истинную метку» — есть ли у пары хоть одна MRS3-стратегия с
   `total_pnl_pct`, приведённым к 30 дням, ≥ 10% при `max_drawdown_pct` ≤ 15%.
2. Посчитать AUC: насколько хорошо число хороших точек в подсетке скринера
   (304) предсказывает эту истинную метку. Сравнить с AUC по полной сетке.
3. Сообщить, сколько пар попало в эту сверку.

## 5. Что вернуть

Верни **один markdown-файл** со следующими разделами. Таблицы — в markdown
или CSV, компактно (агрегаты, не сырые точки).

1. **Инвентарь данных**: какие источники найдены, сколько пар, какие стороны
   (LONG/SHORT), какие окна дат, сколько точек всего, у каких пар не нашлось
   даты листинга. Есть ли PerformanceDB.
2. **Фактические значения порогов** из `config.local.json` (все, что
   перечислены в разделе 3).
3. **Блок A**: таблица медиан `trades_per_day` (ТФ × сдвиг), таблица
   отношений 5m/4h по сдвигам, точка разворота пулом и разброс по парам.
4. **Блок B**: таблица ошибки разделимой модели, подобранные A и L по ТФ,
   качество подгонки.
5. **Блок C**: таблица доли прохождения фильтра (ТФ × сдвиг), число
   отбракованных хороших точек, найденные артефакты на границах.
6. **Блок D**: доли хороших точек по сдвигу, по ТФ, по open_ma, по close_ma;
   число хороших точек на пару.
7. **Блок E**: таблица «пара → хороших в 5472 → хороших в 304», ранговые
   корреляции для всех проверенных подсеток, вывод о лучшей подсетке и о
   возможности удешевления.
8. **Блок F**: результаты сверки с PerformanceDB, если он был.
9. **Честные оговорки**: размер выборки, что осталось непроверенным, где
   результат неустойчив, где ты сомневаешься в корректности своих расчётов.
10. **Краткий вывод**: 5–10 предложений — что подтвердилось, что
    опровергнуто, что оказалось неожиданным.

Отдельно приложи **CSV с агрегатом по точкам** в таком виде (он нужен для
дальнейшего анализа на моей стороне):

```
symbol,side,timeframe,shift_bp,open_ma,close_ma,n_points,n_economic_pass,n_good,median_trades_per_day,median_pnl30,median_dd_pct
```

Если объём позволяет — приложи также CSV на уровне пары:

```
symbol,side,window_start,window_end,effective_days,n_points_total,n_good_full_grid,n_good_screener_304,best_pnl30,best_shift_bp,best_timeframe
```

## 6. Чего не делать

- Не менять код, не писать в базы, не запускать тестер, не публиковать
  surface.
- Не «улучшать» определения из раздела 3 — даже если они кажутся
  неоптимальными. Если видишь в них проблему, посчитай по ним как есть и
  **отдельно** опиши проблему в оговорках.
- Не выдумывать выводы там, где данных мало. Если на какой-то разрез попало
  мало пар или мало хороших точек — так и напиши, вместе с числом
  наблюдений.
- Не подгонять под гипотезы из раздела 4. Они сформулированы на маленькой
  выборке (8 пар) и вполне могут не подтвердиться.
