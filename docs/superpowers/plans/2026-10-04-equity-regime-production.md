# Equity regime: план внедрения в Performance v2

**Дата:** 2026-10-04. **Статус на 2026-10-05:** план P6 одобрен независимым Claude Opus 5 (`PLAN_APPROVED`); локальная реализация прошла 627 тестов и независимое `CODE_REVIEW_PASS`; миграция действующей БД ожидается.

Контракт статусов и числовых границ: [карта equity regime](../../specs/2026-10-03-equity-regime-status-map.md). Решение о `REJECTED` и ручной очистке: [ADR-0055](../../decisions/0055-equity-filter-rejected-and-manual-fact-cleanup.md). Хранение независимых источников отказа: [ADR-0056](../../decisions/0056-equity-rejection-source-lifecycle.md). Замороженная исследовательская база: [M3](../../reports/2026-10-04-equity-regime-m3-research.md). Действующий R7.3 — baseline; исследовательские статусы не переносятся в живую БД.

## 1. Цель и границы

Внедрить расчёт `GROWING`, `WEAKENING`, `RESUMED`, `STALLED`, `DROP`, `NOT_EVALUATED` по **текущему отчёту**; подключить его отдельно к equity-фильтру и инструменту equity-ранжирования; сохранить объяснимые причины и вывести новые факты в Panel/Excel. При опубликованном жёстком отказе включённого фильтра действующий `User Status` становится `REJECTED` независимо от ручных меток.

Не входят в эту поставку: `REJECT60`, новый `Auto Status`, восстановление старых исследовательских статусов в живой базе, запланированный ретест, автоматическое удаление, переписывание prune и изменение импортёра ради ручной очистки. Очистка тяжёлых фактов после ручного отбора — отдельная работа; здесь их не удаляем.

## 2. Неизменяемые правила расчёта

1. Шестичасовая сетка строится назад от UTC-конца отчёта по правилам покрытия R7.3. `v` — OLS-наклон `ln(equity)` по фактически прошедшим дням ×3000; `p=3000×(ln(Eend)−ln(Estart))/дни`. Для `UP` нужны оба `>2`, для `DOWN` оба `<−2`, для `FLAT` оба по модулю `≤2`; прочее `MIXED`. PRE28 доступен при фактических `≥14` днях.
2. Полный ATH/HWM и DD14/DD7 считаются по всем исходным точкам, а не по шестичасовой сетке. Пробой W7 требует нового полного ATH **после** `T−7d` и конечной equity строго выше `HWM(T−7d)`. ATH на трёх этапах GROWING/WEAKENING сравнивается на границах `T−28`, `T−14`, `T−7`, `T` без двойного зачёта одного рекорда.
3. Сначала техническая пригодность → `NOT_EVALUATED`. Затем собрать **все** применимые жёсткие причины в порядке `DD_14_7_GTE_23`, `W28_DOWN`, `PRE28_AND_W28_NOT_UP`; при любой причине → `DROP`. Далее проверить GROWING, WEAKENING, RESUMED, STALLED в этом порядке. Валидная непокрытая геометрия — не создающий `REJECTED` диагностический `NOT_EVALUATED / UNCLASSIFIED_GEOMETRY`, блокирующий приёмку, а не новый рыночный статус. Перебор комбинаций направлений должен доказать недостижимость этой ветки.
4. GROWING: PRE28=UP, если доступен; W28/W14/W7=UP; три последовательных ATH и удержание W7; либо `v,p≥10` на всех трёх окнах без двух последовательных снижений `v` минимум на 20%, либо `v,p≥7` на W28, `v,p≥10` на W14/W7 и `v28≤v14≤v7`. WEAKENING имеет ту же геометрию, но не проходит оба варианта скорости. RESUMED и STALLED применяют точные ветви из карты; предыдущий сохранённый статус не читают.

## 3. Матрица отбора

| Фильтр | Equity rank | Проходящие состояния | STALLED | DROP / NOT_EVALUATED | Источник REJECTED |
| --- | --- | --- | --- | --- | --- |
| Выкл. | Выкл. | Старый R7.3-путь; классификатор не вызывается | Прежнее поведение | Прежнее поведение | Нет |
| Вкл. | Выкл. | PASS, далее действующее обычное ранжирование | PASS + `RESERVE` | `FILTERED` с жёсткими / техническими причинами | Только для DROP при публикации |
| Выкл. | Вкл. | Equity-порядок GROWING → WEAKENING → RESUMED | `RESERVE` | `FILTERED`, причина `EQUITY_RANK_UNRANKABLE` | Нет |
| Вкл. | Вкл. | PASS и тот же equity-порядок | PASS + `RESERVE` | `FILTERED` с жёсткими / техническими причинами | Только для DROP при публикации |

`FILTERED` в режиме «только ранжирование» — существующий технический исход `Auto Status`, **не решение equity-фильтра и не `User Status=REJECTED`**. В отдельном снимке оценки сохраняются исход расчёта и причина. `NOT_EVALUATED` при любых включённых потребителях исключается из списка, но не создаёт постоянный отказ. `STALLED` не повышается до финалиста даже при недоборе.

При включённом equity-ранжировании непригодные кандидаты исключаются **до** распределения мест. Затем сортируем по классу GROWING → WEAKENING → RESUMED, внутри класса — по действующим ключам equity quality R7.3 с `strategy_id` последним ключом разрешения равенства. Следующие подходящие кандидаты заполняют освободившиеся места. Когда их недостаточно, список финалистов остаётся короче Top N с причиной `EQUITY_RANK_ELIGIBLE_SHORTFALL`; `STALLED`, `DROP` и `NOT_EVALUATED` места не заполняют. Тестировать вытеснение кандидата внутри Top N, равенство ключей и недобор при наличии STALLED.

## 4. Срезы реализации и доказательства

### A. Чистый классификатор

Создать `src/mrs3/performance_v2_equity_regime.py` и `tests/test_performance_v2_equity_regime.py`. Сначала failing tests, затем один ограниченный проход по точкам отчёта и чистое детерминированное решение. Покрыть границы `2`, `7`, `10`, ровно 20%, PRE28 ровно 14 дней, DD ниже/ровно/выше 23%, внутринедельный ATH с потерей пробоя, три независимых этапа ATH, PRE28=DOWN/W28=UP, W28=DOWN при любом PRE28, W28=FLAT/MIXED при недоступном PRE28, все совместные причины, неположительную equity. Для экспоненциальной кривой проверить `v≈p` с явным допуском Decimal.

### B. Версионный кэш и кандидаты отбора

Создать `src/mrs3/performance_v2_equity_regime_cache.py`; изменить `src/mrs3/performance_v2_selection.py` и соответствующие тесты. Использовать имеющийся ключ `(result_id, algo_version)` таблицы `equity_quality_metrics`, её поля `source_revision` и `facts_sha256`, новую версию и проверку целостности фактов. Несовпадение — промах. Preview считает в памяти без DML; **только явный прогрев** делает `UPSERT ... DO UPDATE` по `(result_id, algo_version)` после повторной проверки источника, заменяя устаревшую строку той же версии. Все включённые потребители получают один расчёт. При обоих выключенных переключателях не обращаться к новому классификатору, кэшу или исходной кривой и оставлять новый снимок NULL.

### C. Схема v9 и атомарная публикация

Изменить `src/mrs3/performance_v2_store.py`, `src/mrs3/performance_v2_selection_review.py` и тесты схемы/публикации. Добавить nullable `selection_results.equity_regime_json` и таблицу `strategy_rejection_sources` с ключом `(strategy_id, source_kind, reason_code)` и первым доказательством: result, selection run, версия классификатора, ревизия источника, digest фактов, время UTC. `source_kind` допускает `EQUITY_REGIME_FILTER`, `reason_code` — только три жёстких кода; JSON проверяет codec приложения. **Не менять CHECK `auto_status` и не делать backfill.** `auto_reason` уже `VARCHAR` без CHECK (`src/mrs3/performance_v2_store.py`, схема `selection_results`), поэтому `EQUITY_RANK_UNRANKABLE` не требует новой колонки или значения enum. Переход v8→v9 должен быть повторяемым, транзакционным и проверенным на копии; тест вставляет `FILTERED` с этой причиной в v9.

Перед первой записью `persist_selection_snapshots` проверить актуальные result, strategy mapping, ревизию и digest; расхождение прерывает всю операцию. В одной транзакции сохранить run, результаты со снимком оценки и все причины жёсткого equity-DROP включённого фильтра; повторная причина — `ON CONFLICT DO NOTHING` с сохранением первого доказательства. Позднейшие PASS, ошибки данных и выключение фильтра не стирают источник. Эффективный `User Status=REJECTED`, если есть ручная метка или независимый источник; импорт ручного review не должен удалять equity-источник. Отдельного автоматического сброса нет; ошибочную публикацию можно исправить только отдельной протоколируемой операцией восстановления данных. Проверить две конкурентные публикации одного набора стратегий: транзакционная проверка источника и ключи не допускают частичного снимка или двойной строки первого доказательства. Preview, rank-only DROP, `NOT_EVALUATED` и `UNCLASSIFIED_GEOMETRY` должны оставить таблицу источников без новых строк.

### D. Panel, Excel и совместимость

Обновить читателей эффективного `User Status`, статус/причины/метрики в Panel и выгрузке Excel, а также защиту импорта ручного review. Составить перечень всех потребителей `auto_status` (счётчики, selection queries, Excel, Panel, API, retest и экспорт PerformanceDB) и проверить для каждого, что технический `FILTERED` только ранжирования не считается `REJECTED` или кандидатом в Top N и **не увеличивает счётчик отсеянных equity-фильтром**. При обоих выключенных переключателях на фиксированном времени сравнить прежние значения, причины и байты вывода с baseline; новый JSON NULL и новых записей в кэше/источниках нет.

### E. Замороженный replay и производительность

Сопоставить построчно ровно 30 940 замороженных M3-результатов, включая `NOT_EVALUATED`, **полный набор** жёстких причин и общий digest; непокрытых валидных случаев должно быть ноль. Это измеряемые условия приёмки replay. Прошлые исследовательские числа — только ориентир, не ожидаемый результат. Замерить холодный, Preview с промахами, инкрементальный и полностью прогретый путь; записать время/RSS. Полностью прогретый путь не читает исходные equity-точки; Preview не делает DML. Не вводить произвольный порог времени/RSS без базового замера.

## 5. Проверка, ревью и выпуск

1. Проверить свежую v9, v8→v9, повторную инициализацию, откат при искусственной ошибке и чтение старой v8 без автоматической записи. До работы с живой БД получить проверяемую резервную копию, остановить писателей и испытать восстановление на копии.
2. Запустить узкие и смежные тесты только через `.venv\Scripts\python.exe -m pytest`, задавая `--basetemp` в TEMP на диске C; после тестов удалить только проверенную временную папку. Для изменённого JS — `node --check`; затем `git diff --check` и просмотр staged diff.
3. Перед каждым scoped conventional commit выполнить независимый `review_code` на компактном ASCII-пакете: требования, diff и точные результаты проверок. Исправления проверять повторно. Обновить `progress.md` и PRD при изменении фактического статуса.
4. Живую базу мигрировать только после успешных тестов, replay, независимого ревью и проверки резервной копии. Наличие этого плана не означает, что новые статусы уже применяются в Panel или базе.

## 6. Критерий завершения

На копии базы все строки имеют один объяснимый исход, все жёсткие причины воспроизводимы, Preview не пишет данные, публикация атомарна, четыре сочетания переключателей работают по матрице, а прежний путь с обоими выключенными переключателями остаётся прежним. Тесты подтверждают ноль строк в `strategy_rejection_sources` для Preview, `NOT_EVALUATED` и rank-only-исключения. После отдельного проверенного переноса в рабочую базу Panel и Excel показывают опубликованные новые статусы и эффективный `REJECTED`.
