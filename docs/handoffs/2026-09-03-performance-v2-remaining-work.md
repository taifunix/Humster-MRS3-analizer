# Performance DB v2 — актуальный остаток работ

**Дата сверки:** 2026-09-03
**Назначение:** единый backlog для Performance DB v2 и связанных с ней экранов.
**Граница:** ниже под «стадиями 1–3» понимаются стадии именно Performance DB v2, а не общие фазы MRS3 из `PRD.md`.

## Итог

Контур расчёта, отбора, XLSX и ручного review практически собран. Основной
незакрытый объём — не очередные Pareto, а приёмка текущей Stage 3, надёжный
контур повторной проверки сомнительных отчётов и только затем жизненный цикл
стратегий (`RETEST`, discard и возможное удаление). Полный повторный импорт
всей базы сейчас не является ни утверждённым, ни необходимым действием.

Свежая проверка текущего рабочего дерева:

## Уже реализовано и не является backlog

### Стадия 1

- Один `strategy_performance.duckdb`, одна текущая заменяемая tester-результатная запись на стратегию, типизированные actions/equity и параметры ордеров/плато.
- Транзакционный `ADD`/`REPLACE`, очистка зависимого кэша окон при замене и параллельная подготовка HTML при одном DuckDB writer.
- Окна A/B и четыре хронологических окна с календарной нормализацией к 30 дням. Дата последней сделки не сокращает знаменатель периода.
- Парсер сверяет заявленные tester `Total transactions (buy/sell)` и `Final balance` с данными отчёта. `EndDate` тестера включителен: событие или equity ровно на конце периода допустимы.
- Разовый аудит текущей базы сформирован в [performance-v2-period-integrity-audit-2026-09-02.xlsx](../../Output/performance-v2-period-integrity-audit-2026-09-02.xlsx): `0 CONFIRMED`, `49 HIGH`, `100 REVIEW`. Это результат исследования, а не новая функция панели.

### Стадия 2

- Выбор Pair + Side, локальная перестановка/включение стадий, область `ПАРА+сторона` или `ПАРА+сторона+ТФ`, автоматические счётчики и явный прогрев фактов.
- Все зарегистрированные фильтры и Pareto применяются последовательно к оставшимся строкам; XLSX содержит только включённые колонки стадий в фактическом порядке.
- A/B deterioration, минимальный Shift, plateau Pareto, robust-фильтры, Pareto окна B, Shift/Close-MA near-tie и другие видимые стадии.
- Финальный score использует актуальные веса: Robust PnL `0.30`, Worst DD `0.15`, A/B stability `0.15`, Worst Hold p95 `0.12`, Shift 1 `0.10`, PointsMin `0.09`, Close MA `0.09`.
- Формирование XLSX, его числовые форматы, скрытые audit-колонки, блоки, причины исключения, `BLOCK/PASS`, пастельная раскраска и колонка `Final rank`.

### Стадия 3

- Автоматическая миграция внутренней схемы v2 → v3 в одной транзакции. Она не меняет strategy/result/action/equity и не требует пересчёта `window_metrics`.
- Снимок каждого экспортированного отбора: `selection_runs` и `selection_results`.
- Объединение точных аналогов: Pair + Side + TF + ORD + Close MA; дополнительно допускаются только соседние Close MA при совпадении всех `(analysis_run_id, plateau_id)` ордеров, без транзитивного объединения.
- Автоматические статусы `FINALIST`, `RESERVE`, `ANALOG`, `FILTERED`, `REJECTED`; Top N по умолчанию равен 20.
- XLSX-review: скрытый мета-лист, editable `User Status`, `User Rank`, `Analog Of ID`, `Comment`; обратный импорт одиночных и нескольких файлов из папки; история review append-only.
- Единственный долговременный тег сейчас — `REJECTED`. Он не удаляет никаких фактов.
- A/B-экран умеет выбирать конкретную пару и Strategy ID; «Только финалисты» опирается на последний сохранённый run и его последний review.

## Остаток работ в порядке целесообразности

### S1-A. Закрыть приёмку уже реализованной Stage 3

**Статус:** обязательно перед переходом к новым фичам.
**Почему:** код и тесты есть, но продуктовый путь ещё не подтверждён на реальной базе и Excel.

1. На копии реальной базы открыть панель и подтвердить одноразовую миграцию в schema 3: число существующих strategy/result/action/equity не меняется, `database_instance_id` сохраняется после перезапуска.
2. Экспортировать реальную Pair + Side; открыть файл в Microsoft Excel, изменить допустимые `User Status`/`User Rank`/`Analog Of ID`/`Comment`, сохранить и сделать обратный импорт.
3. Проверить пакетный импорт нескольких XLSX: плохой файл не мешает атомарному импорту другого Pair + Side.
4. Убедиться, что `REJECTED` добавляет/снимает только `strategy_tags`, не удаляя result/actions/equity; «Только финалисты» показывает effective `FINALIST` последнего run по каждой стороне.
5. Независимый code review выполнен; после commit/push перейти к ручной Excel-приёмке на реальной копии базы.

**Не требуется:** пересчёт фактов по всем парам только из-за schema v3; migration не меняет `window_metrics`.

### S1-B. Превратить аудит целостности периодов в поддерживаемый инструмент

**Статус:** согласованная потребность, отдельной спецификации нет.
**Цель:** выбирать кандидатов на повторный тест точнее, чем полный re-import.

Нужен read-only отчёт/кнопка, который заново строит XLSX/таблицу с тремя
классами:

- `CONFIRMED` — только проверяемое нарушение контракта: timestamp вне включительного `[StartDate, EndDate]`, несоответствие индексов/числа actions, несоответствие ORD и сохранённых order rows, нарушение заявленных counters нового HTML;
- `HIGH` — минимум два независимых статистических признака (например большой хвост до конца периода и выраженное отклонение от той же Pair+Side+TF+report-period когорты);
- `REVIEW` — один статистический признак.

Обязательные поля: Strategy ID, Strategy, Result ID, период, first/last action,
last equity, хвост в часах, признаки и параметры воспроизведения всех ордеров.
Последняя сделка до `EndDate` сама по себе не является ошибкой: в корректном
tester-отчёте могут быть дни без сделок и разреженная equity.

До утверждения этой фичи разовый файл выше является рабочим инструментом.

### S1-C. Закрыть источник данных для будущей диагностики

**Статус:** требуется архитектурное решение до реализации.
**Проблема:** старая БД хранит типизированные facts, но не исходный HTML и не весь tester config; поэтому она не способна доказать, что древний HTML был полностью импортирован.

Минимальный безопасный вариант для *новых* импортов:

1. сохранять в `import_files` или отдельной immutable evidence-строке declared `StartDate`, `EndDate`, `Total transactions`, `Final balance`, source hash и фактически разобранные counts;
2. продолжать reject только timestamp строго позже `EndDate` и строго раньше `StartDate`;
3. не требовать sample на конце периода и не вводить проверку «gap между equity points» — эталонный отчёт имеет допустимые суточные промежутки.

Это не восстанавливает первичные HTML старой базы и не должно маскироваться под доказательство их полноты.

### S2-A. Эксплуатационная калибровка отбора, а не новая архитектура

**Статус:** ongoing ручная работа с готовым контуром.

- Сравнивать реальные выгрузки при разных порядке/включении стадий; счётчики уже пересчитываются автоматически, XLSX требует только готовых facts.
- `Trades — нижний статистический порог` остаётся выключенным по умолчанию: IQR не понимает ожидаемую частоту сделок на разных TF и может отбрасывать хорошие 4h-стратегии.
- `Минимальный Shift` также выключен по умолчанию; включать его только при сознательно выбранном пороге.
- `pareto_close_ma_near_tie` сохранён, но выключен по умолчанию: он не должен заранее убирать более сильные варианты только из-за Close MA. Аналоги и финальный score учитывают Close MA безопаснее.

Новых фильтров, корреляционных кластеров или «умных» порогов без отдельной
проверяемой спецификации добавлять не следует.

### S3-A. RETEST из базы

**Статус:** принято ADR-0020, но не реализовано.
**Зависимости:** после S1-A и отдельной спецификации.

Нужен статус/тег `RETEST` отдельно от `REJECTED`, действие панели для ACTIVE
стратегий с этим тегом, явные даты теста и проверка listing date. Контур обязан
генерировать RUNS из типизированных параметров базы, использовать общий
RUNS → inbox → v2 replacement путь, заменять только успешные результаты и
снимать `RETEST` только с них. Частичный успех — нормален; неуспешные остаются
помеченными с причиной.

Текущая Stage 3 хранит только `REJECTED`; расширять `strategy_tags` до RETEST
без отдельного контракта нельзя.

### S3-B. Discard и отдельный reviewed delete для `REJECTED`

**Статус:** не реализовано и сознательно отложено.

1. **Discard:** удалить тяжёлые текущие facts (result/actions/equity/window cache), оставить typed strategy/order/plateau и tags, поставить `lifecycle_status=DISCARDED`.
2. **Удаление:** только отдельный экспорт кандидатов с `REJECTED`, ручной review и явное подтверждение точных targets. Никакого автоматического удаления по тегу.

Обе операции требуют отдельной спецификации, preview, транзакций, rollback и
повторной проверки исторических selection snapshots.

### S3-C. Вход в Portfolio Optimizer

**Статус:** отложен и не должен начинаться автоматически.

Performance DB v2 — будущая граница входа, но portfolio simulation требует
отдельного контракта: timestamps сделок, лимиты позиции/заявок, LONG/SHORT и
hedge/one-way, L2/margin данные. До этого допустим только аналитический Layer A;
нельзя выдавать selection score или DD5 proxy за портфельный результат.

## Устаревшие или заменённые пункты

| Старое намерение | Актуальная трактовка |
| --- | --- |
| Stateless Stage 2 без `selection_runs` и обратного XLSX import | Заменено Stage 3 из spec 2026-09-02: export сохраняет immutable run, review импортируется атомарно. |
| ADR-0021 как следующий шаг | Частично superseded ADR-0022; сохраняются только принципы immutable snapshot/latest run. |
| Top-50, Close-MA near-tie включён по умолчанию, старые веса robust ranking | Заменено: Top-20, Close-MA near-tie выключен по умолчанию, веса `30/15/15/12/10/9/9`. |
| `BELOW_CUTOFF`, отдельный «мусор», generic tags | Не используются. Есть `RESERVE` и единственный durable `REJECTED`. |
| V1 migration/dual read | Не планируется. Рабочий контракт — только Performance DB v2. |
| Fast TEST как отдельный panel workflow | Retired; актуальный тестовый путь — native `SINGLE_MODE`/общий RUNS контур. |
| `ONUSDT_reports` / Tester Report Library v1 | Отдельный старый ONUSDT-вариант, не часть текущего Performance DB v2 backlog. Возвращать только по отдельному решению о долговременном хранении raw HTML. |
| Автоудаление или discard по `REJECTED` | Запрещено без отдельного reviewed удаления. |
| Глобальная проверка непрерывности equity/actions как признак дефекта | Неверна для tester: разрешены длительные периоды без сделок. |
