# Правила работы с Humster MRS3

## Порядок чтения в новой сессии

1. Прочитать этот файл.
2. Прочитать `PRD.md`.
3. Прочитать `progress.md`.
4. Открыть только активную спецификацию, указанную в `progress.md`, и её явные зависимости.
5. Открыть только код, тесты и ADR, на которые ссылается эта спецификация.
6. Читать `docs/archive/` лишь когда активная спецификация ссылается на историческое правило или происхождение решения.

Не читать весь архив по умолчанию и не переносить старый handoff в новую документацию копированием.

## Источники истины

- `PRD.md` — актуальные цели, границы проекта и реестр спецификаций.
- `docs/specs/` — требования и acceptance criteria конкретных фич.
- `docs/decisions/` — неизменяемые решения, меняющие архитектуру, контракт или правила работы.
- `progress.md` — текущая проверенная точка, следующий шаг и блокеры.
- `README.md` — только публичное и подтверждённое описание использования.

При конфликте действуют: утверждённая новая спецификация → ADR → PRD → архив.

## Реализация и документация

Перед изменением поведения создать или обновить спецификацию. В ней фиксировать scope, non-goals, контракты входов/выходов, инварианты, тесты и ссылки на необходимый исторический контекст.

После изменения состояния разработки обновлять `progress.md`. При смене scope или статуса обновлять PRD. При изменении публичного поведения обновлять README только после подтверждения тестами. Значимые технические решения записывать отдельным ADR.

## Git и review

Рабочая ветка по умолчанию — `main`. Перед каждым коммитом обязательны: scoped implementation, пропорциональные тесты, `git diff --check`, независимый review отдельным агентом и устранение подтверждённых замечаний. Автор изменения не может быть обязательным reviewer.

Коммит создаётся только после review. В коммит включаются только связанные файлы: `docs:` для документации, `chore:` для настройки, `refactor:` для сохранения поведения, `feat:`/`fix:` для одной проверяемой функции, `test:` для тестов. Не смешивать фичу, рефакторинг, зависимости и generated artifacts.

## Локальный тестер и данные

Тестер на этой машине задаётся в игнорируемом `config.local.json`; создать его можно копированием `config.local.json.example`. Реальный локальный путь не записывается в отслеживаемую документацию, README или шаблоны. Не коммитить локальные конфиги, HTML, DuckDB, отчёты, результаты тестера, credentials или другие generated artifacts.

Не удалять исходные HTML до подтверждения v4 DuckDB manifest, schema version и `safe_to_delete=YES` для каждого файла.
